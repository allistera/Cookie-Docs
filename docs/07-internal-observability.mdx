The internal monitoring environment runs on Unraid Tower. Prometheus collects and stores metrics, Pyrra translates service-level objectives into Prometheus rules, and Grafana presents those results alongside external application telemetry. Netdata supplies host metrics. [Observability](/observability) covers the application-side Sentry, Honeycomb and Analytics Engine instrumentation.

This document is a configuration snapshot verified on **17 November 2026** using Tower's files, container mounts and arguments, Prometheus's targets API, and Grafana's datasource and dashboard APIs. All four configured scrape targets reported healthy at inspection. This establishes collection reachability, not end-to-end application health or notification delivery. No production configuration was changed for this document.

## Architecture and boundaries

```mermaid
flowchart TB
  subgraph External[External telemetry services]
    CF[Cloudflare Worker telemetry]
    CE[Cloudflare Prometheus exporter Worker]
    V[Vercel deployment API]
    S[Sentry errors and browser telemetry]
    H[Honeycomb Worker traces]
    CF --> CE
  end
  subgraph Tower[Unraid Tower]
    N[Netdata host metrics]
    VE[Vercel exporter]
    P[Prometheus metrics and rule evaluation]
    O[Pyrra objective files]
    F[Pyrra filesystem backend]
    R[Generated recording and alert rules]
    API[Pyrra API and UI]
    G[Grafana dashboards]
    V --> VE
    CE -->|HTTPS metrics scrape| P
    VE -->|Metrics scrape| P
    N -->|Prometheus-format scrape| P
    O --> F --> R --> P
    F -->|Objective API| API
    P -->|PromQL results| API
    P -->|PromQL results| G
    S -->|Datasource queries| G
  end
  U[Operator] --> G
  U --> API
  U --> H
```

Arrows represent data or configuration flow. Prometheus initiates metric scrapes; Grafana and Pyrra query Prometheus. Grafana is a presentation layer, not the metrics store. Pyrra generates rules; Prometheus evaluates them. Honeycomb traces remain outside this metrics pipeline.

The core services use the Docker network `grafana_default`. Grafana's Worker dashboards explicitly select the `tower-prometheus` datasource, which addresses `http://prometheus:9090`; the default Grafana datasource is Sentry. When using Explore, select Prometheus explicitly.

## Collection and retention

| Prometheus job | Target | Interval | Purpose |
| --- | --- | --- | --- |
| `cloudflare-workers` | HTTPS `/metrics` on `cloudflare-prometheus-exporter.cloudflare-581.workers.dev` | 30 seconds | Worker invocation counts, runtime errors and duration percentiles |
| `vercel-cookie-web` | `vercel-exporter:9108/metrics` | 60 seconds, 45-second timeout | Project deployment/build telemetry |
| `tower-netdata` | `192.168.1.123:19999/api/v1/allmetrics?format=prometheus` | 30 seconds | Tower host metrics |
| `prometheus` | `localhost:9090/metrics` | 30 seconds | Prometheus's own runtime metrics |

The global rule evaluation interval is 30 seconds. Prometheus uses retention limits of **15 days** and **10 GB**; either limit can constrain available history. Seven-day SLO calculations require sufficient retained samples. A newly installed or reset series has only the history accumulated since that point.

`up{job="cloudflare-workers"}` reports scrape success. `cloudflare_exporter_up` reports the exporter's upstream collection state. Check both: an HTTP endpoint can respond successfully while its upstream telemetry collection has failed. A healthy scrape also does not independently prove that every exported value is fresh.

## Persistent configuration and data

| Tower path | Container use | Ownership and recovery significance |
| --- | --- | --- |
| `/mnt/apps/appdata/prometheus/config/prometheus.yml` | `/etc/prometheus/prometheus.yml`, read-only mount | Scrape jobs, intervals and rule-file references |
| `/mnt/apps/appdata/prometheus/config/cloudflare-late.yaml` | `/etc/prometheus/cloudflare-late.yaml` | Derived latency, traffic and error recording rules |
| `/mnt/apps/appdata/prometheus/data` | `/prometheus`, writable | Historical metric samples |
| `/mnt/apps/appdata/pyrra/objectives` | `/etc/pyrra` in filesystem backend, read-only | Authoritative SLO definitions |
| `/mnt/apps/appdata/pyrra/rules` | Writable backend output; read-only `/pyrra-rules` in Prometheus | Generated recording and alert rules |
| `/mnt/apps/appdata/grafana/data` | `/var/lib/grafana`, writable | Grafana's saved state |
| `/mnt/apps/appdata/grafana/provisioning/datasources` | `/etc/grafana/provisioning/datasources`, read-only | Provisioned datasource configuration |

Prometheus loads `/pyrra-rules/*.yaml` and `/etc/prometheus/cloudflare-late.yaml`. Preserve objective files as source configuration; hand edits to generated rules can be overwritten. Preserve the existing `/pyrra-rules` mount when recreating Prometheus.

Back up persistent configuration and state using a consistent database/filesystem backup procedure. Configuration recovery restores collection and definitions; restoring metric history requires the Prometheus data as well. Backup scheduling and restore success were not audited here. Keep API credentials out of documentation, dashboard exports and source control.

## How SLOs are calculated

There are 34 objective files covering 17 observed Workers, including the exporter and `northlink-automation` as well as Cookie services. This inventory is broader than Cookie's application Worker list.

```mermaid
flowchart LR
  Req[Invocation counter] --> Rate[Five-minute invocation rate]
  Err[Runtime error counter] --> Rel[Seven-day errors divided by invocations]
  Req --> Rel
  Dur[Exporter P99 duration gauge] --> Gate[At most 0.5 seconds]
  Rate --> Active[Positive traffic and healthy collection]
  Health[Scrape and exporter health] --> Active
  Gate --> Good[Boolean good observation]
  Active --> Good
  Good --> Lat[Seven-day good observations divided by observations]
  Rel --> Budget[Compliance and remaining error budget]
  Lat --> Budget
  Budget --> Dash[Grafana and Pyrra views]
  Rules[Pyrra generated burn-rate rules] --> Alerts[Prometheus alert state]
```

### Reliability

The ratio indicator uses `cloudflare_worker_errors_total` over `cloudflare_worker_requests_total`, filtered by Worker and grouped by account. Reliability is `1 - errors / invocations`. The inspected `cookie-web-emails` objective targets **99.9% over seven days**.

This measures invocations completing without Cloudflare runtime errors. It does not establish HTTP success, reachability, delivery correctness or execution of a missed scheduled job. No invocations means there is no request-based result.

### Latency

`cloudflare_worker:duration_p99_seconds` selects the exporter's `quantile="P99"` gauge. `cloudflare_worker:latency_p99_good` records whether that value is at most **500 ms**, only where five-minute invocation rate is positive and both collection health checks pass.

The latency objective targets **99.9% good active observation intervals over seven days**. It is not a statement that 99.9% of individual requests finished within 500 ms. Each included evaluation contributes an observation rather than a request count; low-traffic and high-traffic intervals are not weighted by their request volumes. The duration units follow the exporter's metric contract.

### Ingestion exception and reset

The live `mail-app-ingest` reliability objective targets **95%**, while its latency objective remains **99.9%**. Both select `slo_reset="20261117T155600Z"`. Prometheus adds that label to ingestion request/error counters at scrape time and to its latency-good recording rule. Those objectives exclude samples before the reset; they do not immediately represent seven complete days.

The current Grafana Worker dashboard still labels its table as a uniform 99.9% target and divides reliability error ratios by `0.001` for budget calculations. Its queries also do not explicitly select the ingestion reset label. Consequently, ingestion's Grafana budget display can disagree with the current Pyrra objective and can combine historical series across the reset. Use the objective definition and its scoped results when interpreting ingestion. This documentation records the discrepancy; it does not change the dashboard.

For any objective, remaining budget is `1 - bad_fraction / (1 - target_fraction)`. Negative remaining budget means the allowance has been exceeded. A missing denominator or absent signal must remain unknown, rather than being presented as perfect compliance.

## Dashboards and alerts

| Dashboard UID | Use |
| --- | --- |
| `cookie-app-overview` | Cross-source Worker, Sentry and Vercel overview |
| `cookie-workers-slos` | Worker status, compliance, error budgets, traffic, errors and P99 duration |
| `cookie-web-sentry` | Frontend issues and performance |
| `cookie-web-vercel` | Vercel deployments and builds |

The Vercel dashboard explicitly states that runtime observability is unavailable on the current plan. The Sentry dashboard description mentions historical exporter gauges, but the inspected Prometheus scrape configuration has no Sentry exporter job. Treat historical descriptions as insufficient evidence of a current ingestion path.

The inspected Pyrra objectives enable burn-rate alerts and disable absent-series alerts. The Worker dashboard counts `ALERTS` with `alertname="ErrorBudgetBurn"` and `alertstate="firing"`. That proves what the panel queries, not that a notification reaches an operator.

The inspected Prometheus configuration contains no `alerting` destination block. Although Grafana has an Alertmanager datasource, this does not establish a Prometheus-to-Alertmanager notification route. End-to-end delivery, receivers and notification policies remain unverified. A Tower outage also removes this monitoring stack's own view of the incident; it is not an independent external availability monitor.

## Operational checks

```mermaid
flowchart TD
  Start[Missing or unhealthy panel] --> Scrape{Prometheus target up?}
  Scrape -->|No| Network[Check endpoint, container, DNS and network]
  Scrape -->|Yes| Export{Exporter upstream healthy?}
  Export -->|No| Upstream[Check exporter logs, API access and upstream service]
  Export -->|Yes| Traffic{Recent traffic and metric samples?}
  Traffic -->|No| Unknown[No signal: inspect traffic and freshness]
  Traffic -->|Yes| Rules{Recording rules loaded and evaluating?}
  Rules -->|No| Config[Check objective generation, mounts and rule errors]
  Rules -->|Yes| Panel[Check datasource, filters, reset labels and target assumptions]
```

Start with Prometheus `/targets`, `/rules` and `/alerts`. Useful Explore queries against `tower-prometheus` include:

```text
up
cloudflare_exporter_up{job="cloudflare-workers"}
cloudflare_worker:requests_per_second:rate5m
cloudflare_worker:error_ratio:rate5m
cloudflare_worker:duration_p99_seconds
ALERTS{alertname="ErrorBudgetBurn",alertstate="firing"}
```

Run the following read-only configuration checks on Tower after a monitoring change:

```sh
docker exec prometheus promtool check config /etc/prometheus/prometheus.yml
docker exec prometheus sh -c 'promtool check rules /pyrra-rules/*.yaml /etc/prometheus/cloudflare-late.yaml'
curl -fsS http://127.0.0.1:9090/-/ready
curl -fsS http://127.0.0.1:9090/api/v1/targets
```

For an SLO change, edit the objective source, confirm backend generation, validate the generated rules, and confirm Prometheus loaded the expected expressions. Then compare Pyrra with Grafana using the same target, time window and label filters. A file on disk, a successful reload and a rendered panel are separate checks.

For a telemetry outage, restore collection before interpreting budgets. For an application failure with healthy telemetry, follow the service-specific Sentry, Honeycomb and platform-log investigation paths in [Observability](/observability#where-to-look-first).
