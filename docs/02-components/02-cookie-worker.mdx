description: The six Cloudflare Workers — three that serve Cookie-Web's browser API, and three that ingest inbound mail, run overnight AI enrichment, and flush scheduled sends.

Cookie-Worker hosts Cookie's independently deployable Cloudflare Workers. Each Worker owns its source, tests, generated environment types, local secret template, and Wrangler config under `workers/<name>/` — a directory becomes a "Worker capsule" simply by containing a `wrangler.jsonc`, so adding one needs no other registry or CI change. Shared code lives in a root module only once at least two Workers actually use it (see `shared/auth.js`, `shared/fetch.js`, `shared/openai.js`).

## Workers

Six Workers run here, in two groups. The first three answer HTTP requests made
directly by Cookie-Web's browser app and each hold a custom domain; the last
three have no public URL and are driven by inbound email or cron.

| Worker | Trigger | Public domain | Purpose |
| --- | --- | --- | --- |
| `cookie-web-labels` | HTTP (browser) | `labels-api.infinitywave.online` | Label and label-rule CRUD — `GET/POST/PATCH/DELETE /labels` and `/labels/rules` |
| `cookie-web-messages` | HTTP (browser) | `messages-api.infinitywave.online` | Single-message read, state changes, and unsubscribe — `GET/POST/PATCH /messages`, plus `/messages/attachment`, `/messages/thread-body`, `/messages/contacts` |
| `cookie-web-tasks` | HTTP (browser) | `tasks-api.infinitywave.online` | AI Today cards and the Documents store — `GET/POST /tasks` with `/tasks/refresh`, `/tasks/interests`, `/tasks/daily-note-seed`, `/tasks/image-upload`, plus `/documents` |
| `mail-app-ingest` | Email, scheduled (15 min) | — | Parse and store inbound mail, forward the original, enrich the stored copy |
| `data-enricher` | Scheduled (05:00 UTC daily), manual | — | Todoist tasks due today, AI analysis of important mail, recent-inbox triage, personalised news round-up — feeds Cookie-Web's AI Today page |
| `scheduled-send-flusher` | Scheduled (every 5 min) | — | Calls Cookie-Web's `POST /api/send?resource=flush` so "Send Later" mail goes out once due; owns no send logic itself |

```sh
npm run workers          # list discovered Worker capsules
npm run dev -- mail-app-ingest
npm run dev:all          # one Wrangler session, supports service bindings
npm run deploy -- mail-app-ingest   # production deploys never accept --all
```

## Cookie Web API Workers

`cookie-web-labels`, `cookie-web-messages`, and `cookie-web-tasks` differ from
the other three: they are called by a real `fetch()` from user-facing
JavaScript in the browser, not server-to-server behind a shared token. Each one
took over a route that used to be a Vercel Function in Cookie-Web
(`api/labels.js`, `api/messages.js`, `api/tasks.js`), so the endpoint names
survived the move but the origin changed.

Three consequences follow from being browser-facing, and all three share them:

- **Auth0 access tokens, verified per request.** The same bearer token the
  Vercel functions take. Authorization binds the verified issuer and immutable
  `sub` to `users.auth0_sub`; a token's email claim never selects a mailbox.
- **CORS matters.** Each Worker answers preflight and echoes an allowlisted
  origin (`shared/cors.js`): the production app, any localhost port, and
  `*.vercel.app` preview deployments. Cookie-Web's own CSP has to allow the
  domains in turn — `connect-src` includes `https://*.infinitywave.online`.
- **Custom domains, not `workers.dev`.** The three domains above are declared
  in each Worker's `wrangler.jsonc` routes and hard-coded in Cookie-Web's
  [`src/lib/apiWorkers.js`](https://github.com/allistera/Cookie-Web/blob/main/src/lib/apiWorkers.js).
  Change one and both sides must move together. Each Worker still answers on its
  `workers.dev` URL, which is kept for debugging.

All three reach Supabase over the same `HYPERDRIVE` binding the mail Workers
use — there is no separate database, and no RPC back to Vercel.

:::note
`cookie-web-tasks` is the largest of the three: besides the AI Today cards it
owns the whole Documents feature — folders, blocks, tags, and image upload.
Document search itself is served by the `cookie-web-search` Worker's Meilisearch
hybrid index, the same as mail search.
:::

## mail-app-ingest

Cookie's Cloudflare Email Worker — the entry point for every inbound message. Forwarding to the real mailbox is the primary outcome; storage, AI, and monitoring failures never intentionally block it.

```text
Cloudflare Email Routing
  -> parse MIME
  -> store idempotently through Hyperdrive (+ apply matching tag rules)
  -> forward original email
  -> close ingest database client
  -> waitUntil(AI classification on a fresh client)
```

<FileTree>

- src/
  - worker.js — entry point, orchestrates the flow above
  - parse.js — MIME parsing
  - attachments.js — uploads attachment bytes to private Vercel Blob storage
  - store.js — idempotent storage transaction (by user + RFC Message-ID)
  - rules.js — user-defined tag rules, applied synchronously in the storage transaction
  - enrich.js — OpenAI classification (auto-tagging, spam scoring)
  - synthetic-id.js — stable IDs for messages without a usable Message-ID
  - sentry.js — sanitised error reporting (no email or model content)

</FileTree>

Notable behavior:

- Rejects parsing above 10 MiB while still forwarding the original.
- Only spam scored **≥ 0.98** moves a message into the Spam folder.
- A 15-minute cron retries stale pending/failed AI work, three messages per run.
- Transient forwarding errors are re-thrown so the sending server retries; permanent forwarding errors are accepted only once the message is stored safely.

## data-enricher

Runs daily and on demand to populate Cookie-Web's AI Today page.

<FileTree>

- src/
  - worker.js — entry point; `POST /run`, `?phase=today`, `?phase=digest`
  - todoist.js — gathers tasks via a remote Todoist **MCP server** (not one Cookie hosts)
  - analyze.js — AI task-analysis of important/unread email
  - digest.js — applies Reply Needed, Review, and Noise triage to the last 24 hours of Inbox mail
  - news.js / news-sources.js — GitHub, Product Hunt, and BBC UK round-up, ranked against the user's stored interests
  - store.js — reads/writes the enrichment tables (tasks, digest, news, interests)
  - mcp.js — MCP **client** helper used to reach the Todoist MCP server over streamable HTTP

</FileTree>

`POST /run?phase=today` rebuilds both AI Today cards and is what Cookie-Web's `POST /api/tasks?resource=refresh` calls; the legacy `?phase=digest` name rebuilds inbox triage alone. Triage scans recent mail regardless of read state, shows Reply Needed and Review groups, and stores Noise as category counts only. Its policy is adapted from [Eric Porres's Email Triage Plugin](https://github.com/ericporres/email-triage-plugin); Cookie implements the rules in its existing Worker rather than running the plugin or a Gmail integration. Product Hunt and GitHub tokens are optional — their sections are simply skipped without them, since one daily unauthenticated GitHub search request is well inside the rate limit.

:::note
`data-enricher` was originally prototyped in Python and rewritten in JavaScript: vendored PyPI packages pushed the bundle past the free-plan size cap, and Python still lacks a Hyperdrive driver.
:::

## scheduled-send-flusher

The simplest Worker: every 5 minutes it calls `POST /api/send?resource=flush` on Cookie-Web using a shared bearer token (`COOKIE_WEB_FLUSH_TOKEN` here, `SCHEDULED_SEND_FLUSH_TOKEN` on the Cookie-Web side). Cookie-Web owns claiming due `scheduled_sends` rows and calling Resend — this Worker is purely a clock.

## Configuration highlights

| Name | Scope | Purpose |
| --- | --- | --- |
| `HYPERDRIVE` | all except scheduled-send-flusher | Binding to the Supabase connection |
| `AUTH0_DOMAIN` / `AUTH0_AUDIENCE` | the three `cookie-web-*` Workers | Verify the browser's Auth0 access token |
| `ALLOWED_ORIGIN` | the three `cookie-web-*` Workers | Production origin added to the CORS allowlist |
| `ENRICHER_RUN_URL` | cookie-web-tasks | Where `/tasks/refresh` calls `data-enricher` |
| `OWNER_EMAIL` | mail-app-ingest, data-enricher | The exact Cookie-Web user email that owns stored messages |
| `AI_MODEL` | mail-app-ingest, data-enricher | Classification / task-analysis / triage / news-ranking model |
| `OPENAI_API_KEY` | mail-app-ingest, data-enricher | Classification, task analysis (`/v1/responses` only — no Worker calls `/v1/embeddings` at runtime) |
| `HTTP_TRIGGER_TOKEN` | data-enricher, scheduled-send-flusher | Shared secret authorizing each Worker's own `POST /run` |
| `TODOIST_API_TOKEN` | data-enricher | Bearer token for the Todoist MCP server |
| `PRODUCT_HUNT_TOKEN` / `GITHUB_API_TOKEN` | data-enricher | Optional; enrich the news round-up |
| `COOKIE_WEB_FLUSH_TOKEN` | scheduled-send-flusher | Must match Cookie-Web's `SCHEDULED_SEND_FLUSH_TOKEN` |

## Deployment

Production deployment is manual via the GitHub Actions `Deploy` workflow, which is dispatched with one Worker's directory name. It validates the whole repository, dry-runs the selected Worker again, and publishes only that Worker — each Worker syncs only its own scoped secrets, so none receives another's credentials.

:::tip
See the repository's `RUNBOOK.md` for the full deployment checklist, AI-recovery steps, credential rotation, and rollback procedure.
:::
