Cookie-Worker hosts thirteen independently deployable Cloudflare Workers. A directory under `workers/<name>/` becomes a discoverable Worker capsule by containing a matching `wrangler.jsonc`; root tooling finds it for type generation, checks, dry-runs, and deployment. Shared modules live under `shared/` only when multiple Workers need them.

## Worker inventory

Ten Workers serve Cookie's browser APIs on custom domains; three run from email or scheduled triggers.

| Worker | Trigger | Purpose |
| --- | --- | --- |
| `cookie-web-ai` | HTTP | `POST /compose` and `/summarize`; shared durable AI quota |
| `cookie-web-calendar` | HTTP | `/calendar-events`, `/calendars`, and `POST /calendar-availability`, including recurrence, ICS sync, fresh availability reads, and natural-language event drafts |
| `cookie-web-emails` | HTTP | keyset-paginated `/emails` lists, `/emails/state` bootstrap, and composer preferences |
| `cookie-web-labels` | HTTP | label and label-rule CRUD |
| `cookie-web-messages` | HTTP | message body/state/labels/unsubscribe, attachments, thread bodies, and contacts |
| `cookie-web-notifications` | HTTP | `/notification-event` claim/ack lease for browser notifications |
| `cookie-web-receipts` | HTTP + email clients | authenticated receipt status plus an unauthenticated, flood-guarded tracking pixel |
| `cookie-web-search` | HTTP | Meilisearch mail/federated search, saved mail views, and mailbox Q&A |
| `cookie-web-send` | HTTP + service binding | immediate/scheduled Resend delivery, cancellation, follow-up state, and `/send/flush` |
| `cookie-web-tasks` | HTTP + service binding | AI Today, Tasks/projects/subtasks, Documents, preferences, and enricher refresh |
| `mail-app-ingest` | Email + 15-minute cron | inbound parse/store/forward, classification, indexing, and recovery |
| `data-enricher` | Hourly cron + HTTP | inbox triage only |
| `scheduled-send-flusher` | 5-minute cron | invokes `cookie-web-send` to flush due scheduled messages |

The ten `cookie-web-*` APIs use custom `*-api.infinitywave.online` domains and keep `workers.dev` enabled for debugging. Their shared CORS policy permits the production SPA, localhost ports, and Vercel preview deployments. Auth0 bearer verification is shared through `shared/auth-jwt.js`; the receipt pixel and bearer-protected send flush are the deliberate authentication exceptions.

## Composer preferences API

`cookie-web-emails` exposes `GET` and `PUT /emails/compose-preferences` at the `emails-api` origin. Both require the normal Auth0 bearer token. The verified issuer and `sub` identify the provisioned `users` row; an email address in the request or token never chooses the owner. Responses use `Cache-Control: private, no-store`.

`GET` returns the account's document, or empty defaults when unset:

```json
{
  "revision": 0,
  "signatureHtml": "",
  "snippets": []
}
```

`PUT` sends that full shape with the revision most recently read. Each snippet has a stable `id`, unique lowercase slug `name` (the slash trigger), and nonempty `html`, for example `{ "id": "...", "name": "hello-world", "html": "<p>Hello</p>" }`. The Worker accepts at most 50 snippets, a 50-character trigger, 65,536 characters per HTML field, and a 512 KiB request. Reserved built-in slash commands cannot be used as names. Rich HTML is untrusted data: clients must sanitize before sending and before placing returned markup into an editor or preview. Cookie-Web uses its existing DOMPurify policy for both directions.

A successful `PUT` returns the complete document with an incremented `revision`. An outdated revision returns HTTP `409` with `{ "error": "Compose preferences changed in another session", "current": { ...latest document... } }`; clients should retain the user's unsaved draft, show the latest document, and require an explicit decision before retrying. Invalid documents return `400`; unsupported methods return `405`. Authentication rejects an unprovisioned subject with `403`; a user row that disappears after authentication returns `404` from this handler. The conditional per-user update stores this document under `users.prefs.composePreferences` and preserves unrelated preference keys. No schema migration is required.

## Saved mail views API

`cookie-web-search` exposes authenticated `GET` and `PUT /saved-views` at the `search-api` origin. The verified Auth0 issuer and `sub` select the provisioned user; the request cannot choose another owner. Responses use `Cache-Control: private, no-store`. Views live under `users.prefs.savedSearchViews`, separately from categories and other preference keys; no schema migration is required.

`GET` returns `{ "revision": 0, "views": [] }` when unset. `PUT` sends the full document with the revision most recently read. A view has a stable UUID `id`, a unique 1–60 character `name`, a 1–470 character `query`, and `folder` set to `all`, `inbox`, `sent`, `spam`, `snoozed`, or `done`. At most 30 views can be stored; their array order is the sidebar/command order. `query` supports words plus one each of `from:` or `sender:`, `to:`, `tag:`, `has:attachment`, `before:YYYY-MM-DD`, and `after:YYYY-MM-DD`. The folder is a separate field; a top-level `in:` in the saved query is rejected. Quoted operator values keep their contents literal, including text such as `in:inbox` within a tag value. Boolean syntax, recognized operators with unsupported prefixes such as `-from:alice`, `is:starred`, repeated operators, and malformed dates are rejected rather than treated as free text. The normal `GET /search` route remains the result API: the client appends `in:<folder>` and requests `scope=mail&mode=keyword` with `limit` and `offset`. `estimatedTotalHits` is an estimate, not an exact count.

For saved-view navigation, `GET /search` opts into `pagination=verified` alongside `scope=mail&mode=keyword`. This keeps existing hybrid/federated clients unchanged. The response adds `nextOffset` (a raw indexed-hit offset, or `null`) and `scanLimitReached` (Boolean). The Worker hydrates up to `limit` owned mail results and looks ahead for one more live result before returning `nextOffset`; stale indexed hits are skipped, so clients must use the returned offset rather than calculate `offset + limit` or rely on `estimatedTotalHits`. Offsets must be decimal integers from 0 through 999. The scan is bounded to the first 1,000 indexed hits; when it reaches that bound without proving an end, `scanLimitReached: true` warns that later matches may exist. A `null` next offset with that warning is not a confirmed end-of-results.

An accepted `PUT` returns the full document with an incremented revision. An outdated revision returns `409` with `{ "error": "Saved views changed in another session", "current": { ...latest document... } }`; clients should retain their unsaved draft and ask the user to review the latest document before retrying. Invalid data returns `400`; unsupported methods return `405`. An owner row that disappears after authentication returns `404`. Deleting a view is a `PUT` omitting its definition and never changes messages. Separate views can match the same message, and this API does not alter Important/category deduplication.

## Availability read API

`POST /calendar-availability` on `cookie-web-calendar` uses the standard Auth0 owner binding. Its JSON request contains `calendarIds` (1–10 unique owned UUIDs), `from` and `to` (inclusive dates, at most 31 days), `timeZone` (proposal/range zone), `interpretationTimeZone` (for native, floating, and date-only times), and `confirmFloatingTimes: true`. Both zones must be recognized IANA timezone identifiers. Requests are limited to ten per minute per user and responses use `Cache-Control: no-store`.

The read resolves subscription URLs from owned calendars and reapplies the current HTTPS host allowlist. Fresh feed downloads reuse the existing 10-second timeout, 5 MiB size limit, DNS/public-address checks, and redirect refusal. It reads native event masters in the bounded range with a 32-day lookback for long or overnight events, expands recurrence, and unions overlapping busy intervals. It does not write cached events or subscription sync metadata.

A complete response contains `complete: true`, `busy` as numeric epoch-millisecond `{ start, end }` intervals, the checked `window`, `checkedAt`, and per-calendar `sources`. Subscription sources distinguish the fresh range's `checkedAt` from cached `subscriptionSyncedAt` and `cachedSyncFailed`. Event titles, descriptions, and feed URLs are omitted. A failed, unsupported, or capped source returns `complete: false` with an empty `busy` array and a safe error; clients must not interpret that empty array as free time.

Native recurrence follows Cookie's daily/weekly/monthly/yearly model, including selected weekdays. Fresh ICS checks use node-ical's expansion for daily/weekly/monthly/yearly RRULEs, EXDATE exclusions, and individual RECURRENCE-ID overrides; explicit source timezones preserve instants across DST. Date-only ends are exclusive. Cancelled and transparent events do not block times. Unknown source timezones, ambiguous floating/native times, RDATE, EXRULE, RANGE overrides, VFREEBUSY components, subdaily or multiple-times-per-day rules, and unsupported/non-Gregorian rules block suggestions. Dates before 1970 in a feed, durations over 30 days, more than 1,000 feed events or native masters, more than 5,000 busy occurrences, and native recurrence beyond safe stepping limits also fail closed. Users can select another calendar or range; cached rows are never a fallback for incomplete coverage.

ICS `DURATION` values support only positive elapsed hours, minutes, and seconds (`PT…`, optionally prefixed with `+`), bounded to 30 days. Nominal day/week forms such as `P1D` or `P1W`, malformed values, and unsupported duration parameters make the source incomplete before parsing; this avoids incorrect daylight-saving boundaries and parser logging of raw values. All-day events with explicit, exclusive `DTEND` remain supported. A producer using nominal durations must supply explicit end dates/times before that feed can provide availability suggestions.

## Cross-Worker calls

Two service bindings keep internal orchestration on Cloudflare's network:

- `cookie-web-tasks` binds `ENRICHER` to `data-enricher`; `POST /tasks/refresh` forwards an authenticated, owner-checked rebuild request.
- `scheduled-send-flusher` binds `SEND` to `cookie-web-send`; every five minutes it calls `POST /send/flush` with the shared bearer secret.

Both target Workers retain public routes for operations/debugging, so their token checks still apply to service-binding calls.

## mail-app-ingest

```text
Cloudflare Email Routing
  -> parse MIME and calendar invites
  -> store idempotently through Hyperdrive (+ deterministic label rules)
  -> upload attachments to private Vercel Blob, best effort
  -> forward the original email
  -> waitUntil(classification + Meilisearch sync on a fresh client)
```

Forwarding is primary. Parsing above 10 MiB, optional storage/indexing, AI, attachment, or monitoring failures never intentionally block it. Only spam scored at least `0.98` moves out of Inbox. The 15-minute cron retries up to three stale pending/failed classifications and also repairs eligible search-index drift without re-forwarding mail.

**Interactive version:** [inbound mail flow diagram](/Cookie-Docs/diagrams/inbound-mail.html).

## Search and drift repair

Meilisearch owns keyword/semantic ranking for three indexes: `messages`, `documents`, and `tasks`. Writes attempt a best-effort sync and stamp `search_indexed_at` only after the Meilisearch task finishes successfully. Monitoring is bounded to 20 seconds per task. Document/task handlers schedule this work after saving, using a separate database connection, and stamp only the row version that was indexed. Failed or superseded writes leave the watermark stale; manual reindex and drift-repair workflows reconcile those rows later.

`GET /search` without `scope` keeps the mail-only response used by existing clients. `scope=all|mail|documents|tasks` returns a federated response for Cookie-Web's unified search page. Subtask text is folded into its top-level task's search document. `POST /ask` remains owner-scoped mailbox retrieval plus an OpenAI answer with sources.

## Uploaded files (`cookie-web-tasks`)

Files uploaded to Documents are handled by `cookie-web-tasks` under `/files`. Bytes go to the private R2 bucket `cookie-files` (binding `FILES`); metadata goes to `document_files`. Any MIME type is accepted up to 25 MB, with 60 uploads per user per minute.

| Route | Behaviour |
| --- | --- |
| `GET /files?folder=<uuid\|root>` | Lists the caller's files in one folder |
| `POST /files` | `multipart/form-data` with `file` and optional `folder`. The declared `Content-Length` is checked before the body is read; the object is written first and removed again if the metadata insert fails |
| `GET /files/:id` | Metadata for one owned file |
| `GET /files/:id/content` | The bytes, served `inline` only for sniffed JPEG, PNG, GIF, WebP, and PDF, otherwise as an `attachment`, always with `nosniff` |
| `PATCH /files/:id` | Rename, or move to another owned folder or the root |
| `DELETE /files/:id` | Deletes the row, then the object; a failed object delete is reported to Sentry, not surfaced |

Without the `FILES` binding the upload route answers `503`, so a Worker deployed before the bucket exists degrades cleanly.

## AI-assisted unsubscribe

`cookie-web-messages` handles standards-based one-click and `mailto:` unsubscribe first. When a sender offers only a web page, an optional AI tier can inspect the untrusted page, propose one bounded form submission, and verify the result. URL, redirect, form, size, timeout, and public-address checks constrain the model; login, CAPTCHA, JavaScript-only, or ambiguous flows fail closed.

## data-enricher

`data-enricher` runs inbox triage only: Reply Needed / Review rows and Noise counts for the last 24 hours of Inbox mail, stored as `daily_digest` summaries. An hourly UTC cron checks the owner's saved Europe/London schedule (default every day, 09:00–19:00 inclusive). The saved model defaults to `gpt-5-nano`.

Authenticated `POST /run`, `POST /run?phase=today`, and the legacy `POST /run?phase=digest` all run the same triage phase. Manual refresh bypasses the schedule gate. `cookie-web-tasks` continues to call the `today` alias, so existing clients need no migration.

News fetching, news ranking, and per-email task extraction no longer run. Existing `daily_news` snapshots and extracted email tasks remain stored and readable through `GET /tasks`; no replacement news job is scheduled. GitHub and Product Hunt credentials are no longer needed by this worker. Incoming-message classification in `mail-app-ingest` remains a separate pipeline.

## Commands and validation

```sh
npm run workers
npm run dev -- mail-app-ingest
npm run dev:all
npm run types -- --all --check
npm run typecheck
npm test
npm run dry-run -- --all
```

`dev:all` starts every config in one Wrangler session so service bindings work locally. Production deploys accept `all` or one Worker name; each selected Worker is dry-run again before publish.

| `BLOB_READ_WRITE_TOKEN` | ingest and document images | Private Vercel Blob access |
| `ENRICHER_TRIGGER_TOKEN` | tasks/enricher pair | Protect on-demand AI Today rebuilds |
