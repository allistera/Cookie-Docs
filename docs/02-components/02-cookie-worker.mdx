Cookie-Worker hosts thirteen independently deployable Cloudflare Workers. A directory under `workers/<name>/` becomes a discoverable Worker capsule by containing a matching `wrangler.jsonc`; root tooling finds it for type generation, checks, dry-runs, and deployment. Shared modules live under `shared/` only when multiple Workers need them.

## Worker inventory

Eleven Workers serve Cookie's browser APIs on custom domains, cookie-mcp serves the MCP connector, and three run from email or scheduled triggers.

| Worker | Trigger | Purpose |
| --- | --- | --- |
| `cookie-web-ai` | HTTP | `POST /compose` and `/summarize` on a shared durable AI quota; `POST /compose-suggest` (the composer's [writing suggestions](/ai-features#writing-suggestions)) on a quota of its own |
| `cookie-web-calendar` | HTTP | `/calendar-events`, `/calendars`, and `POST /calendar-availability`, including recurrence, ICS sync (listing the calendars also refreshes, in the background, the two stalest subscriptions last synced more than 12 hours ago), fresh availability reads, and natural-language event drafts |
| `cookie-web-emails` | HTTP | keyset-paginated `/emails` lists, `/emails/state` bootstrap, composer preferences, and out-of-office settings |
| `cookie-web-labels` | HTTP | label and label-rule CRUD |
| `cookie-web-messages` | HTTP | message body/state/labels/unsubscribe, attachments, the attachment library, thread bodies, contacts, calendar invitation state, and the list of subscriptions |
| `cookie-web-notifications` | HTTP + cron | `/notification-event` claim/ack lease for browser notifications; `GET/PUT/DELETE /ntfy` settings (per-user server, topic and encrypted access token) and the every-minute publish of queued new-mail alerts to each user's ntfy server |
| `cookie-web-receipts` | HTTP + email clients | authenticated receipt status plus an unauthenticated, flood-guarded tracking pixel |
| `cookie-web-search` | HTTP | Meilisearch mail/federated search, saved mail views, and mailbox Q&A |
| `cookie-web-send` | HTTP + service binding | immediate/scheduled Resend delivery, automatic replies, calendar invitation replies, cancellation, follow-up state, agent send confirmations, and `/send/flush` |
| `cookie-web-tasks` | HTTP + service binding + hourly cron | AI Today, Tasks/projects/subtasks/labels/saved filters, Todoist sync, Documents, preferences, and enricher refresh |
| `mail-app-ingest` | Email + 15-minute cron | inbound parse/store/forward, classification, indexing, and recovery |
| `data-enricher` | Hourly cron + HTTP | inbox triage only |
| `scheduled-send-flusher` | 5-minute cron | invokes `cookie-web-send` to flush due scheduled messages and automatic replies |

The eleven `cookie-web-*` APIs use custom `*-api.infinitywave.online` domains and keep `workers.dev` enabled for debugging. Their shared CORS policy permits the production SPA, localhost ports, and Vercel preview deployments. Auth0 bearer verification is shared through `shared/auth-jwt.js`; the receipt pixel and bearer-protected send flush are the deliberate authentication exceptions.

## Composer preferences API

`cookie-web-emails` exposes `GET` and `PUT /emails/compose-preferences` at the `emails-api` origin. Both require the normal Auth0 bearer token. The verified issuer and `sub` identify the provisioned `users` row; an email address in the request or token never chooses the owner. Responses use `Cache-Control: private, no-store`.

`GET` returns the account's document, or empty defaults when unset:

```json
{
  "revision": 0,
  "signatureHtml": "",
  "snippets": []
}
```

`PUT` sends that full shape with the revision most recently read. Each snippet has a stable `id`, unique lowercase slug `name` (the slash trigger), and nonempty `html`, for example `{ "id": "...", "name": "hello-world", "html": "<p>Hello</p>" }`. The Worker accepts at most 50 snippets, a 50-character trigger, 65,536 characters per HTML field, and a 512 KiB request. Reserved built-in slash commands cannot be used as names. Rich HTML is untrusted data: clients must sanitize before sending and before placing returned markup into an editor or preview. Cookie-Web uses its existing DOMPurify policy for both directions.

A successful `PUT` returns the complete document with an incremented `revision`. An outdated revision returns HTTP `409` with `{ "error": "Compose preferences changed in another session", "current": { ...latest document... } }`; clients should retain the user's unsaved draft, show the latest document, and require an explicit decision before retrying. Invalid documents return `400`; unsupported methods return `405`. Authentication rejects an unprovisioned subject with `403`; a user row that disappears after authentication returns `404` from this handler. The conditional per-user update stores this document under `users.prefs.composePreferences` and preserves unrelated preference keys. No schema migration is required.

## Out-of-office API and delivery

`cookie-web-emails` exposes authenticated `GET/PUT /emails/out-of-office`, using
the verified Auth0 subject's `users` row and private/no-store responses. Preferences
live in `users.prefs.outOfOffice`; unrelated preferences are preserved. A full
`PUT` has `revision`, `enabled`, `startDate`, `endDate` (inclusive `YYYY-MM-DD`),
`timeZone` (IANA), `subject` (up to 998 bytes, no controls), and `text` (plain text,
up to 10,000 characters). A successful save increments the revision and uses a
server activation timestamp. Invalid data is `400`; stale revisions are `409`
with the current settings. Other owners cannot read or mutate these records.

`GET` returns the settings, computed `status` (`disabled`, `scheduled`, `active`,
`expired`), and up to 20 unresolved failed/uncertain delivery records. `PUT` with
`{ "action": "stop" }` disables the latest revision regardless of the caller's
cached revision. `PUT` with `{ "action": "resolve", "deliveryId": "<uuid>",
"outcome": "delivered" }` or `"not_delivered"` records a verified manual outcome;
it never resends. Confirmed delivery starts a fresh four-day cooldown; confirmed
non-delivery releases the sender hold for future arrivals. Resolved rows remain
durable deduplication history.

Migration `0082_out_of_office.sql` adds an inbound revision snapshot trigger on
`messages`, plus RLS-protected, server-only `out_of_office_deliveries` and
`out_of_office_senders`. It explicitly revokes browser-role privileges and keeps
server-role access; no Supabase Auth UUID assumptions or global grants change.
There is no backfill or default enablement. A snapshot failure leaves mail
ineligible without failing storage. `messages.auto_reply_suppressed` is the
screening seam: sender screening/blocking sets it before exposing a decision;
it does not change forwarding. Dispatch locks and rechecks the message and its
classification, skipping busy rows with `NOWAIT`.

The existing bearer-authenticated `/send/flush` runs the unchanged scheduled-send
leg first and preserves its response. Automatic work uses `waitUntil` and its own
database connection, so it does not consume the scheduled caller's existing
20-second HTTP deadline. It scans at most 25 arrivals and attempts at most 10
automatic deliveries within one shared 20-second dispatch budget. Database time
also consumes that budget; no later dispatch starts after it expires, and each
provider timeout is limited to the remaining time (at most ten seconds). Platform
interruption leaves committed leases recoverable on the next flush. A 22-second
watchdog closes a stalled dedicated database client, leaving cleanup margin within
Cloudflare's shared [30-second HTTP background limit](https://developers.cloudflare.com/workers/platform/limits/#duration).
It requires a matching arrival
revision, database `created_at` within the activation/window, completed non-spam
classification, and loop/list/self-mail eligibility. Each queued payload is
immutable, including the configured From identity and fixed loop headers
`Auto-Submitted: auto-replied`, `X-Auto-Response-Suppress: All`, and
`Precedence: bulk`. Untrusted Reply-To is ignored; a reply targets the normalized
envelope sender. Sent copies use existing storage/search integration without a
tracking pixel or attachments.

Eligibility also requires the persisted envelope destination in parsed To/Cc;
Bcc-only deliveries are suppressed. This follows the conservative recipient and
reverse-path guidance in [RFC 3834](https://www.rfc-editor.org/rfc/rfc3834#section-4).
Resend's high-level email API does not expose a null SMTP MAIL FROM control, so
Cookie cannot guarantee the RFC's recommended null reverse-path. It does not fake
a Return-Path header or claim full RFC compliance. The four-day sender cooldown
is Cookie's explicit product policy.

The state machine is `pending → sending → sent`; known first-attempt provider
rejections become `failed`, ineligible unattempted mail becomes `suppressed`, and
ambiguous outcomes become `uncertain`. An atomic owner-locked claim commits a
two-minute lease, unique claim token, stable `out-of-office/<delivery UUID>` key,
and one reservation in the existing ten-sends-per-minute quota before dispatch.
Retries neither charge twice nor refund a possibly consumed reservation. Unknown
transport outcomes retry with backoff only within 23 hours of the first attempt,
with a maximum of 12 attempts; expired or conflicting outcomes require manual
review. The provider retains keys for [24 hours](https://resend.com/docs/dashboard/emails/idempotency-keys).
An uncertain sender stays blocked until resolved, even after four days. Do not
delete unresolved state or bypass the queue to retry at the provider.

Responder serialization uses `lockOutOfOfficeDispatch(tx, userId)` from
`shared/outOfOffice.js`: the transaction advisory lock
`pg_advisory_xact_lock(hashtext('cookie.out-of-office'), hashtext(userId))`.
PostgreSQL's [two-integer advisory key space](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)
is separate from ingest's single-bigint `hashtextextended(userId, 0)` lock.

Short claim/config/manual-resolution transactions acquire the responder lock
first, then the ingest-owner advisory lock, user row and any delivery,
message/classifier (`NOWAIT`), sender and quota rows, in that order. Settings saves
keep their brief ingest-owner lock so revision/activation writes remain atomic
with the arrival snapshot. Enqueue does not acquire the responder lock or hold
an ingest-owner/user lock while waiting for it; delivery rechecks queued snapshots.

Dispatch takes only the responder advisory lock, its delivery row and the
original message/classifier rows; it reads `users` without a row lock. Neither
ingest's advisory lock nor `users FOR UPDATE` spans provider I/O. This also avoids
blocking the `KEY SHARE` user-row checks that inbound foreign keys need. An End
now/config/resolve waiter obtains the responder lock before borrowing any ingest
lock, so waiting for a slow provider does not stall new inbound storage or
forwarding. Ingest's existing five-second storage budget is unchanged. Provider
calls remain fixed-origin and abortable at ten seconds or the remaining background
budget. Successful End now means no later dispatch begins; it cannot recall a
provider request already underway. Provider/body/header content and credentials
are excluded from responder logs.

For sender screening, initial suppression of a new arrival belongs in the
uncommitted ingest transaction and must **not** acquire the responder lock.
Post-ingest block/screen changes must acquire `lockOutOfOfficeDispatch` first,
before any ingest-owner advisory, user, message or classifier locks; set
`messages.auto_reply_suppressed = true` with an owner predicate before committing
and exposing the decision. A change to owner-wide blocking rules uses the same
order. Never acquire the responder lock from inside an already owner-/row-locked
transaction. This serializes suppression with dispatch without putting provider
latency on new-mail ingestion; a successful block cannot retract a provider
request already underway.

Merge the migration first and await **Migrate Database** success,
then deploy the compatible ingest and updated emails/send Workers, then the Web
settings and Docs. Accounts remain disabled throughout rollout. Use GitHub Actions
for unit/E2E verification; migration execution and any controlled delivery checks
belong to the release operator.

## Sender decisions and screening

Migration `0088_sender_screening.sql` follows `0087`. Its server-only
`sender_decisions` table is keyed by `(user_id, address)`, enables RLS and revokes
all privileges from `PUBLIC`, `anon` and `authenticated`. Values are `accepted`
or `blocked`. No historical incoming/contact/sent-address backfill occurs.
`users.prefs.senderScreening` is a strict boolean, absent/false by default;
updates preserve other preferences, including out of office.

The `messages_screen_sender` BEFORE INSERT trigger persists
`messages.screening_status` as `allowed`, `held` or `blocked`. It reads the
displayed `from_address` under ingest's existing owner advisory transaction,
before the notification trigger can queue events. Explicit block wins; acceptance
bypasses screening only. On a lookup error, the message is stored as held with
`auto_reply_suppressed = true`, preserving storage and forwarding while failing
closed for alerts/replies. Sent messages and legacy rows default to allowed.
Ingest never acquires the responder dispatch lock.

Authenticated `GET /emails/senders` returns `{ enabled, decisions, nextCursor }`
with at most 50 decisions. `after=<address>` pages the normalized address order;
`q=<text>` narrows the list to keys containing the text (lower-cased, `LIKE`
wildcards matched literally) and pages with the same cursor;
`address=<address>` reads the one decision that applies to that sender (its own
row, else the most specific `@domain` row). Decision keys are either an exact
address or `@domain`, which covers that domain and its subdomains; the database
resolves them with `effective_sender_decision` (migration 0089), used
by the arrival trigger and the notification Workers. `PUT /emails/senders` takes
an `action`: `settings` with boolean `enabled`; `block`, `accept`, `unblock` or
`forget` with an `address` (an email address or a bare domain); or `restore` with
an owned `messageId`. An address on a company domain writes an `@domain` key; an
address on a public email provider writes an exact-address key, and a bare public
provider domain is rejected. Accept and Block also delete the named sender's own
older exact-address row so the new decision applies to it; Unblock and Remove
delete both the domain key and that row when their decision matches. The
response returns the key (`address`), its stored `decision`, the `effective`
decision for the named sender, and `related`, the other sender addresses whose
held mail moved. Block can include an owned `messageId` belonging to that sender
to withhold the reader's message. Malformed addresses and mismatched ownership
are rejected.

Every mutation obtains `lockOutOfOfficeDispatch` first, then ingest's owner lock,
then the user/message rows. Blocking suppresses replies on all existing inbound
rows the decision now blocks (those whose own effective decision is blocked),
clears their pending alert events, and moves only the selected message and
previously-held mail. Each moved message is re-screened by the decision that
applies to its own sender. Acceptance releases
held mail; unblocking returns it to held while screening is enabled or allowed
otherwise. Restoring one message is refused while its sender remains blocked.
Read/archive/spam/snooze fields are never changed by these mutations.
`auto_reply_suppressed` stays true on previously-withheld mail after release;
no queue replay occurs. A changed disposition clears `search_indexed_at`;
bulk sender decisions invalidate stored thread summaries in the same transaction.

`GET /emails?folder=screening` and `folder=blocked` use normal owner-scoped keyset
pagination and ignore independent archive/spam/classifier state. Ordinary mailbox
queries and counts exclude withheld rows. Search and Ask recheck Postgres during
hydration, so stale index entries cannot reveal held mail; index synchronization
reuses its existing exclusion flag until the drift sweep catches up. Thread
history, summaries, extracted tasks and AI Today live message hydration exclude
withheld rows. Digest snapshots record all contributing message IDs, including
noise; the whole generated snapshot is hidden when a contributor is now held,
so overview prose cannot reveal hidden content. Older snapshots without IDs use
a conservative check of the original 24-hour source window. Freshly generated
digests only use allowed mail. The retention sweep never deletes held mail. It
soft-deletes blocked mail on the owner's `spamRetentionDays` (default 30),
counted from the later of the message's `created_at` and the `updated_at` of the
sender decision that covers it, and rechecks `screening_status` on the row it
updates so a Block, Unblock or Accept that commits first wins. Blocked mail that
arrived within the retention period is passed over before its sender decision is
looked up, since it cannot have expired yet.

The notification trigger queues alerts only for allowed arrivals, but still emits
content-free realtime refresh pings. Browser notification claims recheck current
disposition and the exact sender block; ntfy does so in its batch selection and
again before every publish/retry. The responder reads persisted suppression at
enqueue, claim and dispatch. An already-handed-off alert or provider request
cannot be retracted.

Release order: await full CI on the Web and Worker branches, including the
mandatory PostgreSQL migration tests in Cookie-Worker. Then merge the migration
to Cookie-Worker's `main` and await **Migrate Database**;
deploy `mail-app-ingest`, `cookie-web-notifications`, `cookie-web-send`,
`cookie-web-messages`, `cookie-web-search`, `cookie-web-ai`, `cookie-web-tasks`,
`data-enricher`, then `cookie-web-emails` last; then publish the Web interface and Docs.
The messages/send/ingest Workers consume the changed shared search-index mapping.
All updated Workers require `0088`; none may deploy before migration success.
Keep screening and the responder disabled and do not create sender decisions
throughout the staged rollout. Existing rows and ordinary new arrivals remain
allowed during that interval. Deploying the decision API last ensures all read,
retention and delivery guards are active before it can create held mail.

Cookie-Worker's `Lint and Test` job supplies an isolated PostgreSQL 17 service named
`cookie_screening_test`. Its migration regression file refuses non-loopback or
other database names and fails CI if the test connection is missing. It applies
the actual `0080`, `0082` and `0088` SQL above a small synthetic pre-0080 schema
fixture; it does not emulate Supabase realtime infrastructure or execute the
entire historical migration chain. Worker suites cover authenticated actions,
notification delivery/retries, responder suppression and lock concurrency.

## Saved mail views API

`cookie-web-search` exposes authenticated `GET` and `PUT /saved-views` at the `search-api` origin. The verified Auth0 issuer and `sub` select the provisioned user; the request cannot choose another owner. Responses use `Cache-Control: private, no-store`. Views live under `users.prefs.savedSearchViews`, separately from categories and other preference keys; no schema migration is required.

`GET` returns `{ "revision": 0, "views": [] }` when unset. `PUT` sends the full document with the revision most recently read. A view has a stable UUID `id`, a unique 1–60 character `name`, a 1–470 character `query`, and `folder` set to `all`, `inbox`, `sent`, `spam`, `snoozed`, or `done`. At most 30 views can be stored; their array order is the sidebar/command order. `query` supports words plus one each of `from:` or `sender:`, `to:`, `tag:`, `has:attachment`, `before:YYYY-MM-DD`, and `after:YYYY-MM-DD`. The folder is a separate field; a top-level `in:` in the saved query is rejected. Quoted operator values keep their contents literal, including text such as `in:inbox` within a tag value. Boolean syntax, recognized operators with unsupported prefixes such as `-from:alice`, `is:starred`, repeated operators, and malformed dates are rejected rather than treated as free text. The normal `GET /search` route remains the result API: the client appends `in:<folder>` and requests `scope=mail&mode=keyword` with `limit` and `offset`. `estimatedTotalHits` is an estimate, not an exact count.

For saved-view navigation, `GET /search` opts into `pagination=verified` alongside `scope=mail&mode=keyword`. This keeps existing hybrid/federated clients unchanged. The response adds `nextOffset` (a raw indexed-hit offset, or `null`) and `scanLimitReached` (Boolean). The Worker hydrates up to `limit` owned mail results and looks ahead for one more live result before returning `nextOffset`; stale indexed hits are skipped, so clients must use the returned offset rather than calculate `offset + limit` or rely on `estimatedTotalHits`. Offsets must be decimal integers from 0 through 999. The scan is bounded to the first 1,000 indexed hits; when it reaches that bound without proving an end, `scanLimitReached: true` warns that later matches may exist. A `null` next offset with that warning is not a confirmed end-of-results.

An accepted `PUT` returns the full document with an incremented revision. An outdated revision returns `409` with `{ "error": "Saved views changed in another session", "current": { ...latest document... } }`; clients should retain their unsaved draft and ask the user to review the latest document before retrying. Invalid data returns `400`; unsupported methods return `405`. An owner row that disappears after authentication returns `404`. Deleting a view is a `PUT` omitting its definition and never changes messages. Separate views can match the same message, and this API does not alter Important/category deduplication.

## Availability read API

`POST /calendar-availability` on `cookie-web-calendar` uses the standard Auth0 owner binding. Its JSON request contains `calendarIds` (1–10 unique owned UUIDs), `from` and `to` (inclusive dates, at most 31 days), `timeZone` (proposal/range zone), `interpretationTimeZone` (for native, floating, and date-only times), and `confirmFloatingTimes: true`. Both zones must be recognized IANA timezone identifiers. Requests are limited to ten per minute per user and responses use `Cache-Control: no-store`.

The read resolves subscription URLs from owned calendars and reapplies the current HTTPS host allowlist. Fresh feed downloads reuse the existing 10-second timeout, 5 MiB size limit, DNS/public-address checks, and redirect refusal. It reads native event masters in the bounded range with a 32-day lookback for long or overnight events, expands recurrence, and unions overlapping busy intervals. It does not write cached events or subscription sync metadata.

A complete response contains `complete: true`, `busy` as numeric epoch-millisecond `{ start, end }` intervals, the checked `window`, `checkedAt`, and per-calendar `sources`. Subscription sources distinguish the fresh range's `checkedAt` from cached `subscriptionSyncedAt` and `cachedSyncFailed`. Event titles, descriptions, and feed URLs are omitted. A failed, unsupported, or capped source returns `complete: false` with an empty `busy` array and a safe error; clients must not interpret that empty array as free time.

Native recurrence follows Cookie's daily/weekly/monthly/yearly model, including selected weekdays. Fresh ICS checks use node-ical's expansion for daily/weekly/monthly/yearly RRULEs, EXDATE exclusions, and individual RECURRENCE-ID overrides; explicit source timezones preserve instants across DST. Date-only ends are exclusive. Cancelled and transparent events do not block times. Unknown source timezones, ambiguous floating/native times, RDATE, EXRULE, RANGE overrides, VFREEBUSY components, subdaily or multiple-times-per-day rules, and unsupported/non-Gregorian rules block suggestions. Dates before 1970 in a feed, durations over 30 days, more than 1,000 feed events or native masters, more than 5,000 busy occurrences, and native recurrence beyond safe stepping limits also fail closed. Users can select another calendar or range; cached rows are never a fallback for incomplete coverage.

Only native occurrences whose dates can reach the requested range (with a two-day margin for time zones) are converted, so an ambiguous time well outside the range does not make the check fail.

ICS `DURATION` values support only positive elapsed hours, minutes, and seconds (`PT…`, optionally prefixed with `+`), bounded to 30 days. Nominal day/week forms such as `P1D` or `P1W`, malformed values, and unsupported duration parameters make the source incomplete before parsing; this avoids incorrect daylight-saving boundaries and parser logging of raw values. All-day events with explicit, exclusive `DTEND` remain supported. A producer using nominal durations must supply explicit end dates/times before that feed can provide availability suggestions.

## Sending limits and refusals

`POST /send` on `cookie-web-send` allows ten immediate sends a minute per mailbox, and 300 sends or schedules in a 24-hour window on top of that; past either it answers `429`. A delivery the provider refused is `422` `DELIVERY_REJECTED` with no `Retry-After`, because the same request would only be refused again; Cookie-Web lets that draft be edited and sent again. A failure before the provider was called (an attachment that could not be read, for example) is `503` `DELIVERY_NOT_SENT`: retrying with the same request id resumes the same delivery, and the failed try does not count as a delivery attempt.

An MCP agent's `cookie_send_email` also needs a `confirmation` from the owner. The owner creates one in Cookie under Automations, Connections, **Send confirmations**, with **Create send confirmation**, which calls `POST /send/confirmation`: it answers a browser session only, refuses an agent with `403`, and allows ten a minute. A confirmation is 64 hex characters, valid for ten minutes and bound to the first request id it is used with, so retries of that email succeed and another email needs a new one. Without a valid confirmation, `/send` answers an agent `403` `SEND_CONFIRMATION_REQUIRED`. Browser sends never need one.

### Send error contract

Every failure of `POST /send`, immediate or scheduled, is one row of this table, whether the caller is Cookie-Web, Cookie-iOS or an MCP agent. The coded rows are `SEND_ERROR_CONTRACT` in `workers/cookie-web-send/src/sendErrorContract.js`, and Cookie-Worker's `docs/delivery-and-search-recovery.md` keeps the same table. In the last column, **Release** frees the request id so the draft can be edited and sent anew, **Retry** keeps the draft locked and retries the same unchanged request, and **Surface** keeps it locked and shows the error without retrying.

| Code | HTTP status | Meaning | May have been sent | Client |
| --- | --- | --- | --- | --- |
| `DELIVERY_REJECTED` | `422` | The provider refused this exact message | No | Release |
| `DELIVERY_NOT_SENT` | `503`, `Retry-After: 5` | Recorded, but stopped before the provider was called | No, though the recorded delivery can still go out on a retry or the cron | Retry |
| `DELIVERY_PENDING` | `503`, `Retry-After: 5` | Another attempt holds the lease, or the provider gave no clear answer. Cookie-Web also reports a send with no answer within 25 seconds, or a network failure, under this code | Maybe | Retry |
| `DELIVERY_UNCERTAIN` | `409` | Five attempts or the 23-hour window passed without a provider answer | Maybe | Surface; never retry with a new request id |
| `DELIVERY_CONFLICT` | `409` | The request id was already used for different content | An earlier email under that id may have been | Surface |
| `DELIVERY_REQUEST_ID_REQUIRED` | `409` | A request without a request id matches a completed send older than 24 hours | The earlier one was; this one was not | Release; a new email needs a new request id |
| `SEND_CONFIRMATION_REQUIRED` | `403` | An agent send or schedule has no valid confirmation for this request id | No | Release |
| `SEND_CONFIRMATION_UNAVAILABLE` | `503` | The confirmation table is missing | No | Retry later |
| none | `400` | Invalid JSON, recipients, subject or body, `attachmentIds`, `sendAt` or `followUpAt`, or attachments over the size limit | No | Release |
| none | `401` | Missing or invalid access token | No | Release |
| none | `403` | Mailbox access is not provisioned | No | Release |
| none | `404` | Reply target or attachment not found | No | Release |
| none | `413` or `415` | Body over 4.5 MB, or not JSON | No | Release |
| none | `429` | Per-minute quota (10), daily cap (300), or 50 pending scheduled sends | No | Release |
| none | `500` | Unexpected failure while scheduling or before delivery | No for a schedule; a recorded immediate delivery resumes on retry | Retry |
| none | `502` | Unexpected failure in the delivery step | Unlikely; a recorded delivery resumes on retry | Retry |
| none | `503` | Sending is not configured, or the quota check failed | No | Retry |

Only `DELIVERY_PENDING` and `DELIVERY_NOT_SENT` carry `Retry-After`; the `409` codes must not be retried automatically, so they have none. The scheduled-send flush maps the same codes onto the row: `DELIVERY_NOT_SENT` and `DELIVERY_PENDING` leave it pending, `DELIVERY_REJECTED` marks it failed, and `DELIVERY_UNCERTAIN` or `DELIVERY_CONFLICT` mark it uncertain. Calendar invitation replies (`POST /send/invitation-reply`) have their own mapping, described under [Calendar invitations](#calendar-invitations).

## Cc and Bcc recipients

`POST /send` on `cookie-web-send` takes optional `cc` and `bcc` beside `to`. Each is a comma-separated list of addresses, as `to` is. A blank or absent line means nobody; a line that is present but unusable (an entry that is not an address, or not a string) rejects the request with `400` instead of sending without it. To, Cc and Bcc together are limited to 20 recipients.

Both lines are passed to Resend as `cc` and `bcc`, kept in the delivery ledger with the rest of the frozen request, and written to the sent copy's `messages.recipients`, Bcc included. They join the idempotency key and the scheduled-send request hash only when someone is on them, so a request without copies keeps the key it had before these lines existed.

- **Send Later.** `scheduled_sends.cc_addresses` and `bcc_addresses` hold the lines until the flush delivers them. `DELETE /send/scheduled` returns them as `ccAddresses` and `bccAddresses` so the composer can reopen the message as it was.
- **Drafts.** `cookie-web-drafts` accepts `cc` and `bcc` on `POST /drafts` and `PATCH /drafts/:id` and returns them from `GET /drafts/:id`. A client that sends neither field leaves the stored lines alone, so an older client saving over a draft does not wipe them. The list summary carries only `to`.

The four columns come from migration `0114`. Both Workers read them through `to_jsonb(row) ->> 'cc_addresses'`, which answers `NULL` for a column that does not exist yet, and write them with a statement of their own that runs only when a line is used or has changed. A Worker deployed before the migration therefore behaves as it did; only a draft or a Send Later that has a Cc or Bcc line fails, visibly, until the migration is applied.

## Draft retention

`mail-app-ingest`'s 15-minute cron deletes drafts that are not starred and are more than 30 days past the later of `drafts.updated_at` and `drafts.retention_from`, at most 500 per tick. It is the same delete as `DELETE /drafts/:id`, so the draft's attachment rows go with it. The statement repeats its conditions on the row it deletes, so a star or a save that commits while it waits for that row keeps the draft. A tick that deletes anything logs `drafts_purged` with `deleted`; a failure logs `draft_purge_failed` and is reported to Sentry without stopping the other sweeps.

`PUT /drafts/:id/star` on `cookie-web-drafts` takes `{ "starred": true }` or `false` and answers `{ "draft": { "id", "isStarred" } }`, `400` for any other body and `404` for a draft the caller does not own. The list and single-draft reads return `isStarred`. The route leaves `updated_at` alone, so a star never conflicts with a composer's next autosave, and removing a star sets `retention_from` to the current time.

A composer still holding a draft that the sweep has deleted gets `404` on its next save, and Cookie-Web then saves the message as a new draft.

Both columns come from migration `0119`, which sets `retention_from` on existing drafts to the time it runs.

## Calendar invitations

Two Workers handle an invitation received by email. `cookie-web-messages` records what each mail says about the event when it is read; `cookie-web-send` answers the organiser. Both keep the event's calendar entries in step through `shared/calendarInvitation.js`. The tables are in the [data model](/data-model) (migration `0113`).

An invitation is identified by the iCalendar `UID` and, for one occurrence of a repeating event, that occurrence's `RECURRENCE-ID`. Each `METHOD:REQUEST` or `METHOD:CANCEL` attachment is one revision of it, ordered by `SEQUENCE` and then `DTSTAMP`.

`GET /messages/calendar-invite?id=<message>` returns `calendar_invite` (the event **Add to calendar** offers, unchanged) and `calendar_invitation`, which is `null` for a calendar file that is not an invitation to this mailbox: one with no method, a guest's `REPLY`, or an event the person organised. Reading the message applies its revision:

| The message carries | Effect |
| --- | --- |
| The first revision seen | A new invitation row; nothing on the calendar yet |
| A newer revision | The row and any calendar entry made from it are updated. A higher `SEQUENCE` clears the answer, because the organiser changed what was answered; a newer `DTSTAMP` alone keeps it |
| A cancellation at or after the stored revision | The invitation is marked cancelled and its calendar entry removed |
| The same or an older revision | Nothing changes. The response has `current: false` for an older one and still describes the latest revision |
| A revision naming a different organiser | Ignored: only an event's organiser may change or cancel it |

`calendar_invitation` holds the event's title, location, `start_at`, `end_at` and `all_day`, `recurring` and `occurrence`, the `organizer`, the `attendee` address matched to the person, the `sender` address Cookie sends as, `can_reply` with `reply_blocked` when it is false, the stored `response` and `responded_at`, and `event` (the id and date of the first calendar entry) when it is on the calendar.

`POST /send/invitation-reply` takes `{ invitationId, response, timeZone }`, where `response` is `accepted`, `tentative` or `declined` and `timeZone` is the browser's IANA zone. It mails the organiser an iTIP `REPLY` (RFC 5546) as a `text/calendar; method=REPLY` part (RFC 6047) carrying the invitation's `UID`, `SEQUENCE` and `RECURRENCE-ID`, the organiser, and one `ATTENDEE` with the answer as `PARTSTAT`. It then stores the answer and replaces the invitation's calendar entries, or deletes them for a decline. It answers `{ invitation: { id, response, responded_at, event }, sent }`; `sent` is `false` when the same answer was already on record, in which case no mail goes out and the calendar entry is put back if it had been removed by hand.

| Status | Meaning |
| --- | --- |
| `403` `INVITATION_ALIAS` | The invitation names another of the person's addresses. Cookie sends as `EMAIL_FROM` only and does not answer for an address it cannot send from |
| `403` `INVITATION_NOT_INVITED` | None of the guests is one of the person's addresses |
| `409` `INVITATION_CANCELLED` | The organiser cancelled the event |
| `409` `INVITATION_CHANGED` | The organiser revised or cancelled the event while the reply was being sent |
| `429` | The per-minute sending allowance, shared with `POST /send`, is spent |
| `503` `DELIVERY_PENDING`, `DELIVERY_NOT_SENT` | The provider has not confirmed the reply, or was not reached. Retrying the same request resumes the same delivery |
| `502` `DELIVERY_REJECTED`, `DELIVERY_UNCERTAIN` | The provider refused the reply, or it could not be confirmed in time. The invitation is left unanswered and can be answered again |

Each answer is one delivery in the outbound ledger, keyed by the invitation, the `SEQUENCE` answered, the number of answers already given, and the response. A retry of a request therefore resumes the same delivery and the provider is never asked to send it twice, while a change of mind, including back to an earlier answer, is a new delivery.

Calendar entries are placed on the clock of the `timeZone` sent with the answer, and later revisions reuse that zone. A daily, weekly, monthly or yearly series becomes one repeating row; weekdays and month days carry over only when the first occurrence falls on the same date in the organiser's zone and the person's. Any other rule stores the first occurrence alone. An all-day invitation is one row per day.

`cookie-web-messages` and `cookie-web-send` must hold the same `EMAIL_FROM`: the first uses it to report whether an invitation can be answered, the second enforces it.

## mail-app-ingest

```text
Cloudflare Email Routing
  -> parse MIME and calendar invites
  -> store idempotently through Hyperdrive (+ deterministic label rules)
  -> upload attachments to private Vercel Blob, best effort
  -> forward the original email
  -> waitUntil(classification + Meilisearch sync on a fresh client)
```

Forwarding is primary. Parsing above 10 MiB, optional storage/indexing, AI, attachment, or monitoring failures never intentionally block it. A message the parser cannot read is forwarded once and accepted without being stored, logged as `store_skipped_parse_failed` and reported to Sentry under the `parse` operation, since the same bytes would fail on every redelivery. `List-Unsubscribe` and `List-Unsubscribe-Post` are kept up to 16 KiB, where other header values stop at 2,048 characters, because a cut unsubscribe link does not work. Only spam scored at least `0.98` moves out of Inbox. The 15-minute cron retries up to three stale pending/failed classifications and also repairs eligible search-index drift without re-forwarding mail.

One kind of message is stored but not forwarded: mail the forwarding mailbox itself auto-forwarded to Cookie. Gmail marks its auto-forwards with an envelope sender of the form `<account>+caf_=<recipient>@gmail.com`. When that account is `FORWARD_TO`, Gmail already holds the original, so sending it back added nothing and Gmail rate limited the copies (`421 4.7.28`), which made it redeliver stored messages for hours. The Worker logs `forward_skipped_auto_forwarded` for these and sets `cookie.forward.outcome` to `skipped_auto_forwarded`.

**Interactive version:** [inbound mail flow diagram](/Cookie-Docs/diagrams/inbound-mail.html).

## Search and drift repair

Meilisearch owns keyword/semantic ranking for three indexes: `messages`, `documents`, and `tasks`. Writes attempt a best-effort sync and stamp `search_indexed_at` only after the Meilisearch task finishes successfully. Monitoring is bounded to 20 seconds per task. Document/task handlers schedule this work after saving, using a separate database connection, and stamp only the row version that was indexed. Failed or superseded writes leave the watermark stale; manual reindex and drift-repair workflows reconcile those rows later.

`GET /search` without `scope` keeps the mail-only response used by existing clients; `GET /search?ids=<uuid,...>` (up to 20) returns the owner's messages by id, in the order given and in that same shape, without a Meilisearch query (the assistant drawer uses it to list an answer's emails in the inbox). `scope=all|mail|documents|tasks` returns a federated response for Cookie-Web's unified search page. Subtask text is folded into its top-level task's search document. `POST /chat` streams the assistant drawer's conversation from Meilisearch's conversational search: the Worker validates the conversation, spends the shared `ai` quota, signs a per-request tenant token that pins the model's searches to the owner (`user_id`, and `is_deleted = false` for mail), pushes the chat workspace settings once per isolate, and reduces Meilisearch's OpenAI-shaped stream to `searching`, `sources`, `message`, `token` and `done` events. A conversation holds at most 40 messages; a question may be 4,000 characters, and an assistant answer or a search result 20,000, since every earlier answer is sent back with the next turn. It needs the `MEILISEARCH_CHAT_API_KEY` secret (a key with `search`, `chatCompletions` and `chatsSettings.update`) and answers 503 without it. `POST /ask` remains owner-scoped mailbox retrieval plus an OpenAI answer with sources, kept for older clients. It answers with one JSON response and does not stream; a `stream=1` parameter is ignored.

## Task ordering (`cookie-web-tasks`)

`GET /task-items` lists a project, the Inbox or a label by `position` (migration `0062`), then `created_at`; Today by `due_date`, then `today_position` (`0063`, `NULL` last), then `position`; and a saved filter by due date with undated rows last, then `position`. `POST /task-items/reorder` saves a drag or keyboard move as the rows in their new order rather than a midpoint between neighbours, so a move is one statement and never runs out of precision; the response lists the rows that changed with their new value.

| Body | Behaviour |
| --- | --- |
| `{ ids }` | 1 to 500 distinct task ids. The rows keep the set of `position` values they already held between them, sorted and with any ties pushed `0.001` apart, dealt back out in the requested order; rows outside the set are untouched |
| `{ ids, view: 'today' }` | Numbers `today_position` 1..n in the requested order |
| `{ ids, view: 'today', paged: true }` | One page of Today: the rows keep the `today_position` slots they held, with never-arranged rows slotted after the owner's highest, so other pages are untouched |

Ids the caller does not own are simply absent from the read and so cannot move anyone else's task. Any other `view` is a `400`.

## Todoist sync (`cookie-web-tasks`)

`GET/PUT/DELETE /tasks/todoist` manage one Todoist connection per user: `PUT { token }` verifies the token against Todoist's `GET /api/v1/user`, stores it AES-256-GCM encrypted under the `TODOIST_TOKEN_ENCRYPTION_KEY` secret in `todoist_connections` with the account's email and time zone, and `PUT { enabled?, syncProjects?, syncTasks? }` flips the schedule and the two mirror switches (a flag left out keeps its value). `POST /tasks/todoist/sync` runs a sync at once (four per minute per user). The Worker's hourly cron syncs every enabled connection whose local time is between 07:00 and 20:00.

A run (`src/todoistSync.js`) reads projects, sections, open tasks and recent completions (from an hour before the previous run that read tasks, or the last 30 days on a first run, but never over a window wider than 89 days, as Todoist refuses one over three months), then upserts mirrors keyed by `todoist_id` under the owner's task lock: projects under their parent (the Todoist Inbox maps to the null-project Inbox), sections as `divider` rows named after them, and tasks with inverted priority, normalised labels, due date and time in the task's or account's zone, and a repeat rule when Cookie's recurrence grammar covers it. A task in a project the run does not know goes to the Inbox, after the Inbox's own rows. A mirror Todoist has not changed is left as it is: no rewrite, no activity entry and no reindex. Mirrors Todoist no longer lists as open are completed (if in the completed list) or deleted; vanished projects are deleted when only mirrors depend on them, otherwise unlinked. Cookie-authored rows (`todoist_id IS NULL`) are never changed. With **Sync projects** off (`sync_projects`, migration `0094`) no project row is written, moved or removed and tasks are filed under the mirrored projects Cookie already holds, or the Inbox; with **Sync tasks** off (`sync_tasks`) no section or task row is touched, a vanished project holding tasks is unlinked rather than deleted, only the project list is read from Todoist, and the completion cursor (`tasks_synced_at`) stands still so completions made meanwhile are still found when tasks resume. The last run's status and counts are stored on the connection; a rejected token is recorded without a Sentry event. Without the secret the routes answer 501 and the cron is a no-op.

One thing goes back to Todoist: a mirrored task's completion (`src/todoistPush.js`). When `PATCH /task-items` completes a mirrored task, completes an occurrence of a repeating one, or marks a completed one not done again, the same statement records `close` or `reopen` in `task_items.todoist_pending` (migration `0116`). Once the write has committed, the Worker calls Todoist's `POST /api/v1/tasks/{id}/close` or `/reopen` on the request's deferred queue and clears the column when Todoist answers. Each run sends whatever is still pending before it reads Todoist, at most twenty changes a run, and counts them as `pushed` in its summary. Pushes are serialised per user under an advisory lock, so the push after a `PATCH` and the one at the start of a run cannot both send the same change. A rate limit, server error or timeout leaves the change pending and fails the run, so nothing is applied over a completion Todoist never received; a rejected token fails the run with the reconnect message; any other refusal (the task is gone in Todoist) drops the change. A row still carrying a change when a run writes its plan keeps its completion and due date as Cookie has them and is neither completed nor removed. Nothing is sent while **Sync tasks** is off; the changes go out with the first run after it is switched back on. A request is sent once and never retried in place, because closing a repeating task twice would skip an occurrence. Other edits to a mirrored task are still overwritten by the next run.

## Task comments and attachments (`cookie-web-tasks`)

A task's discussion thread lives in `task_comments` (migration `0096`) and is served under `/task-comments`. Attachment bytes go to the same private R2 bucket as uploads (`cookie-files`, binding `FILES`) under `<user_id>/<uuid>`, with the same 25 MB cap, type sniffing and 60-per-minute rate limit; the row is the source of truth and bytes only ever leave through the attachment route after an ownership check.

| Route | Behaviour |
| --- | --- |
| `GET /task-comments?task=<uuid>[&after=<cursor>]` | The thread of one owned task, oldest first, 100 per page with a `nextCursor`. Each entry carries `body`, `attachment` (`name`, `mimeType`, `sizeBytes`, or null), `mine`, `editedAt` and the stamps; the object key is never sent |
| `POST /task-comments` | `multipart/form-data` with `task`, optional `body` text (up to 10,000 characters) and optional `file`; at least one of the two. The task must be the caller's. The object is written first and removed again if the row insert fails |
| `PATCH /task-comments/:id` | `{ body?, attachment?: null }` on the caller's own entry: replaces the text, or drops the file from an entry that keeps its text; either stamps `edited_at`. An entry can never be left with neither |
| `DELETE /task-comments/:id` | Deletes the caller's own entry, then its object; a failed object delete is reported to Sentry, not surfaced |
| `GET /task-comments/:id/attachment` | The bytes, for the task's owner, served `inline` only for sniffed JPEG, PNG, GIF, WebP and PDF, otherwise as an `attachment`, always with `nosniff` |

`task_comments.task_id` cascades from `task_items`, so deleting a task or a project, or a Todoist run removing a vanished mirror, takes threads with it without the Worker seeing their keys. Each of those paths reads the owner's attachment keys before the delete and, afterwards, removes the objects of the keys that no longer have a row (`attachmentKeysOf` and `deleteVanishedAttachments` in `src/taskComments.js`). Nothing is read back when the owner had no attachments. Without the `FILES` binding a comment with a file answers `503`; text comments still work.

## Document block HTML (`cookie-web-tasks`)

Text in document blocks is Editor.js inline HTML. Before `cookie-web-tasks` stores blocks, it reduces that HTML to basic inline formatting: `b`, `strong`, `i`, `em`, `u`, `s`, `del`, `code`, `a` and `br`, with `href` as the only attribute a link keeps, and only for `http`, `https` and `mailto` links. Every other tag and attribute is removed rather than rejected, so the save still succeeds; `script`, `style` and similar elements go with their content, and relative or `#` links lose their `href`. This covers every writer: document and template saves, `PATCH` of a document's blocks, the daily note seed and the MCP server's document tools, which save through the same routes. It applies to paragraph, header and list text and to image captions; other block types pass through unchanged. The rules match the browser's allow-list in Cookie-Web (`src/lib/documentExport.js`), which still cleans rows written before this check when it shows them. The code is `src/inlineHtml.js`.

## Uploaded files (`cookie-web-tasks`)

Files uploaded to Documents are handled by `cookie-web-tasks` under `/files`. Bytes go to the private R2 bucket `cookie-files` (binding `FILES`); metadata goes to `document_files`. Any MIME type is accepted up to 25 MB, with 60 uploads per user per minute.

| Route | Behaviour |
| --- | --- |
| `GET /files?folder=<uuid\|root>` | Lists the caller's files in one folder |
| `POST /files` | `multipart/form-data` with `file` and optional `folder`. The declared `Content-Length` is checked before the body is read; the object is written first and removed again if the metadata insert fails |
| `GET /files/:id` | Metadata for one owned file |
| `GET /files/:id/content` | The bytes, served `inline` only for sniffed JPEG, PNG, GIF, WebP, and PDF, otherwise as an `attachment`, always with `nosniff` |
| `PATCH /files/:id` | Rename, or move to another owned folder or the root |
| `DELETE /files/:id` | Deletes the row, then the object; a failed object delete is reported to Sentry, not surfaced |

Without the `FILES` binding the upload route answers `503`, so a Worker deployed before the bucket exists degrades cleanly.

## Message threads and labels

A message read from `cookie-web-messages` carries its conversation: the newest 50 messages of the thread, oldest first, leaving out deleted mail and mail held or blocked by sender screening. `POST /messages` adds and removes labels with `add_label`, `remove_label` and `update_labels` (several at once, in one transaction). Each acts only on the owner's user labels: naming a system label such as Spam or Paper Trail answers `404` and changes nothing.

## AI-assisted unsubscribe

`cookie-web-messages` handles standards-based one-click and `mailto:` unsubscribe first. A one-click request counts as an unsubscribe only when the sender answers with a `2xx` status; a redirect is not followed, and like any other answer it falls through to the next method. When a sender offers only a web page, an optional AI tier can inspect the untrusted page, propose one bounded form submission, and verify the result. URL, redirect, form, size, timeout, and public-address checks constrain the model; login, CAPTCHA, JavaScript-only, or ambiguous flows fail closed.

## Requests to URLs from mail or settings

Every fetch of a URL that came from an email or from a user's settings goes through one policy, `requestPublicHttps` in `shared/safe-https.js`: the one-click unsubscribe request, the AI unsubscribe page and form requests, calendar subscription feeds (sync and availability reads), and publishes to a user's ntfy server. Each hop must be an `https` URL without credentials whose host resolves, through a DNS-over-HTTPS lookup, only to public addresses, and must pass the caller's own rule when it has one (the calendar's feed host allowlist, for example). `fetch` never follows a redirect itself: one-click unsubscribe, feeds and ntfy get the `3xx` back and treat it as a failure, while the AI unsubscribe tier follows up to three, checking each new address again. One timeout covers every hop and the body, and a body is read only up to the caller's size cap. An ntfy server whose name resolves to a private address is therefore refused on every publish, which fails like a network error. `cookie-web-messages`, `cookie-web-calendar` and `cookie-web-notifications` also set the `global_fetch_strictly_public` compatibility flag.

## Subscriptions

`GET /messages/subscriptions` on `cookie-web-messages` returns the senders the mailbox is subscribed to, newest mail first, for Cookie-Web's Subscriptions view:

```json
{
  "subscriptions": [
    {
      "address": "news@example.com",
      "name": "Example News",
      "messageId": "…",
      "messageCount": 12,
      "lastReceivedAt": "2026-11-20T08:00:00.000Z",
      "unsubscribedAt": null
    }
  ]
}
```

A sender is one lower-cased `from_address` with at least one received message whose headers include `List-Unsubscribe`. Trash, sent mail, confirmed spam and mail that is held or blocked by sender screening are not counted. `messageId` is the sender's newest such message, the one the client names in `POST /messages` with `action: unsubscribe`. A sender is left out when that message offers nothing the action could use (no valid `mailto:` target and no public HTTPS link), so every listed sender can be acted on. The response is capped at 1,000 senders and never includes the sender-controlled headers themselves.

The query reads only the partial index `messages_list_unsubscribe_idx` (migration `0115`) to find list mail, then the headers of one message per sender. The index predicate is repeated word for word in `subscriptions.js`; the two must change together, or the planner stops using the index and the query goes back to reading every message's headers (about 1.2 s on a 5,000-message mailbox, against a few milliseconds).

A confirmed unsubscribe (`status: unsubscribed` from the one-click, `mailto:` or AI tier) is recorded in `sender_unsubscribes` against the sender's address, and returned as `unsubscribedAt`; the client leaves such a sender out of its list unless `lastReceivedAt` is later, meaning the sender is still writing. A `manual` or `ai_failed` outcome records nothing, because the Worker cannot know whether the person finished on the sender's page. Recording is best effort: if the write fails, the unsubscribe still succeeds and `unsubscribe_record_failed` is logged.

## Attachment library

`GET /messages/attachments` on `cookie-web-messages` returns every file the mailbox received or sent, newest email first, for the Email attachments folder in Cookie-Web's Documents area:

```json
{
  "attachments": [
    {
      "id": "…",
      "filename": "invoice-1042.pdf",
      "contentType": "application/pdf",
      "sizeBytes": 204800,
      "downloadable": true,
      "embedded": false,
      "direction": "received",
      "messageId": "…",
      "subject": "Your November invoice",
      "correspondent": { "name": "Northwind Billing", "address": "billing@northwind.example", "others": 0 },
      "date": "2026-11-20T08:00:00.123Z",
      "unread": false,
      "starred": false,
      "archived": false
    }
  ],
  "nextCursor": null
}
```

| Query | Effect |
| --- | --- |
| `direction=received` or `direction=sent` | Keeps one side of the mailbox; absent lists both. Any other value is a `400`. |
| `embedded=1` | Also lists pictures that belong to an email's body. |
| `before=<nextCursor>` | The next page. Pages hold 100 files; `nextCursor` is `null` on the last one. A malformed cursor is a `400`. |

Nothing is stored for the library. A sent message keeps its files in `attachments` like a received one, so the list is one read over `attachments` and `messages`, with `messages.is_sent` giving the direction. Trash, confirmed spam and mail that is held or blocked by sender screening are left out. `id` is the id `GET /messages/attachment?id=` downloads; `downloadable` is `false` for a file whose bytes were not stored at delivery. The private Blob URL never leaves the Worker. `correspondent` is the sender of a received file or the first `To` recipient of a sent one, with `others` counting the remaining `To` recipients, and is `null` when the mail names nobody. `unread`, `starred` and `archived` describe the email, so the client can open it from the list in the state it is in.

`embedded` is read from the mail rather than recorded at delivery: an image on a message whose HTML shows a `cid:` picture (`src="cid:…"` or `url(cid:…)`). Ingest does not keep which parts were inline, so every image of such a message is treated as part of its body, including a photo attached to an email that also has a logo in its signature; `embedded=1` lists them all. The body is only examined for image attachments. On the production mailbox (about 570 attachments) the read takes about 40 ms.

The cursor is `<sent_at>|<attachment id>` with the timestamp in microseconds, bound as text so that postgres.js does not round it to milliseconds and skip or repeat a row.

## data-enricher

`data-enricher` runs inbox triage only: Reply Needed / Review rows and Noise counts for the last 24 hours of Inbox mail plus mail marked done in that time, stored as `daily_digest` summaries. An hourly UTC cron checks the owner's saved Europe/London schedule (default every day, 09:00–19:00 inclusive). The saved model defaults to `gpt-6-luna`.

Authenticated `POST /run`, `POST /run?phase=today`, and the legacy `POST /run?phase=digest` all run the same triage phase. Manual refresh bypasses the schedule gate. `cookie-web-tasks` continues to call the `today` alias, so existing clients need no migration.

News fetching, news ranking, and per-email task extraction are disabled. Existing `daily_news` snapshots and extracted email tasks remain stored and readable through `GET /tasks`; no news job is scheduled. This worker does not require GitHub or Product Hunt credentials. Incoming-message classification in `mail-app-ingest` remains a separate pipeline.

## Cookie MCP server

`cookie-mcp` is a remote MCP server at `https://mcp.infinitywave.online/mcp` that lets MCP clients such as Claude, Codex, and Hermes work with Cookie mail, labels, drafts, calendar, tasks, and documents through 42 `cookie_` tools. It is an OAuth resource server for Auth0 tokens issued to its own audience (`https://mcp.infinitywave.online/mcp`) and never forwards the client's token. After verifying it, the Worker reaches `cookie-web-emails`, `-messages`, `-labels`, `-search`, `-drafts`, `-send`, `-calendar`, and `-tasks` over service bindings to their `Internal` entrypoint, passing the verified identity as RPC data.

A token needs the `cookie:read` or `cookie:write` scope: `cookie:read` offers only the tools that list, read, and search, and `cookie:write` adds the tools that change something, sending mail included. Reads are annotated read-only; deletes, `cookie_cancel_scheduled`, and `cookie_send_email` are annotated destructive. Mail and document text is untrusted third-party content, and the server tells the model never to follow instructions inside it. `cookie_send_email` needs, besides the send quota, a `confirmation` the owner creates in Cookie for each email (see [sending limits and refusals](#sending-limits-and-refusals)); the agent cannot create one itself. `cookie-mcp` must deploy after the eight Workers it binds; its `Deploy` workflow step is deliberately placed after every `cookie-web-*` step, and a failed step stops the job, so the `all` target already deploys in a safe order. Auth0 setup and the full tool list are in the Cookie-Worker README.

| `cookie_search_tasks` | read | Open tasks by meaning and keywords, up to 50 |
| `cookie_list_task_comments` | read | A task's discussion thread, oldest first; an attachment is named, not returned |
| `cookie_list_task_labels` | read | Task labels with colour and task count |
| `cookie_list_task_filters` | read | Saved task filters with their rules |
| `cookie_list_projects` | read | Every project, flat, with its parent |
| `cookie_create_task` | write | Creates a task or sub-task |
| `cookie_update_task` | write | Changes the fields passed; completes or reopens |
| `cookie_delete_task` | write | Deletes a task and its sub-tasks |
| `cookie_create_project` | write | Creates a project, optionally under a parent |
| `cookie_update_project` | write | Renames, moves, describes or favourites a project |
| `cookie_delete_project` | write | Deletes a project with its sub-projects and tasks |

An agent cannot add a comment (the route takes multipart form data, which the internal entrypoint does not carry), create or edit task labels and saved filters, or reorder tasks.

### Connect a client

Every client uses the URL `https://mcp.infinitywave.online/mcp` and signs in through Auth0 in a browser with the account that owns the Cookie mailbox; no API key is pasted anywhere. Sign-in works only once the Auth0 setup in the Cookie-Worker README is complete. If Auth0 uses a pre-registered application instead of Client ID Metadata Documents, each client also needs that application's client id. To check a connection, ask the client to list your Cookie labels (`cookie_list_labels`), which is read-only.

**Claude Desktop and claude.ai.** Open Settings, then Connectors, choose **Add custom connector**, name it `Cookie`, and enter the URL. A pre-registered client id goes under **Advanced settings**. Choose **Add**, then **Connect**, and sign in. The connector is shared by claude.ai, Claude Desktop, and the mobile apps on the same account. It is not configured in `claude_desktop_config.json`, which is for local servers.

**Claude Code.** Add the server, then run `/mcp`, select `cookie`, and choose **Authenticate**. A pre-registered client id is passed with `--client-id`.

```sh
claude mcp add --transport http --scope user cookie https://mcp.infinitywave.online/mcp
```

**Codex.** Add the server and sign in. A pre-registered client id is passed with `--oauth-client-id` on `codex mcp add`.

```sh
codex mcp add cookie --url https://mcp.infinitywave.online/mcp
codex mcp login cookie
```

**Hermes.** Add the server to `~/.hermes/config.yaml`, run `hermes mcp login cookie`, and use `/reload-mcp` in an open session. A pre-registered client id goes under `oauth.client_id` in the same entry.

```yaml
mcp_servers:
  cookie:
    url: "https://mcp.infinitywave.online/mcp"
    auth: oauth
```
