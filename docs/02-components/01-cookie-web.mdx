Cookie-Web is Cookie's browser client and the owner of the [shared Supabase schema](/data-model). The SPA is deployed at [mail.infinitywave.online](https://mail.infinitywave.online). Its browser-facing APIs have moved almost entirely to the `cookie-web-*` Cloudflare Workers in Cookie-Worker; this repository retains `api/send.js` as a compatibility endpoint used by the current web client. Delivery, retries, and reminders are forwarded to the send Worker; attachment upload authorization and registration remain on Vercel.

## Technology

| Area | Technology |
| --- | --- |
| UI | Vue 3, Pinia, Vue Router, Vite |
| Hosting | Vercel static SPA |
| API | Ten Cloudflare Workers, plus legacy Vercel `/api/send` |
| Authentication | Auth0 |
| Database | Supabase Postgres |
| Realtime | Supabase Realtime broadcast |
| Search | Meilisearch hybrid/federated search |
| AI | OpenAI Responses API |
| Outbound email | Resend |

## Frontend routes

Every route requires Auth0 authentication, enforced by both the `App.vue` render gate and `router.beforeEach`.

| Path | View | Purpose |

| `/` | `AIInboxView` | AI Today: built-in tasks due/overdue, email triage, and personalised news |
| `/inbox` | `TraditionalInboxView` | Classic inbox, labels, folders, search entry, and message actions |
| `/calendar` | `CalendarView` | Calendars, events, recurrence, ICS subscriptions, natural-language event creation, and dated tasks shown on their due date |

| `/search` | `SearchResultsView` | Unified mail, documents, and tasks results; saved mail views use mail-only keyword search |

## API ownership

The production SPA calls Worker custom domains declared in `src/lib/apiWorkers.js`. With the exceptions noted below, each Worker uses the same Auth0 access token and user-binding rule: verified issuer plus immutable `sub` maps to `users.auth0_sub`; email claims never select a mailbox.

| Origin / Worker | Routes used by the web app |
| --- | --- |
| `emails-api` / `cookie-web-emails` | `GET /emails`, `GET /emails/state`, `GET/PUT /emails/compose-preferences` |
| `messages-api` / `cookie-web-messages` | message read/state/unsubscribe, bodies, attachments, contacts |
| `labels-api` / `cookie-web-labels` | label and label-rule CRUD |
| `ai-api` / `cookie-web-ai` | `POST /compose`, `POST /summarize` |
| `calendar-api` / `cookie-web-calendar` | calendar/event CRUD, subscriptions, sync, AI interpretation, and `POST /calendar-availability` |
| `search-api` / `cookie-web-search` | `GET /search` for mail or federated scopes; `GET/PUT /saved-views`; `POST /ask` for mailbox Q&A |
| `tasks-api` / `cookie-web-tasks` | AI Today, task projects/items/subtasks, documents, uploaded files (`/files`), preferences, and refresh |
| `notifications-api` / `cookie-web-notifications` | `POST /notification-event` claim/ack |
| `receipts-api` / `cookie-web-receipts` | authenticated status reads and the unauthenticated tracking pixel |
| `send-api` / `cookie-web-send` | deployed Cloudflare send/schedule API; scheduled flusher calls `/send/flush` over a service binding |
| Vercel `mail.infinitywave.online` | current web-client compatibility calls to `/api/send` for send, schedule, cancel, and follow-up reminders |

:::note
The Cloudflare routes use clean paths instead of the former Vercel `?resource=` multiplexing. Cookie-Web's remaining `/api/send` file is a compatibility path, not evidence that the other APIs still run on Vercel.
:::

## Saved mail views

Open the Mail tab of Search, enter a query, and choose **Save as view**. Name it and select an explicit folder: All mail, Inbox, Sent, Spam, Snoozed, or Done. If the current search contains a supported `in:` folder, the save form moves it into the folder selector. Saved views use keyword search and appear in the Email sidebar and the `/` command palette. They load with the account in another browser. **Manage** in the sidebar lets you rename, reorder, or delete definitions.

Saved queries support words and one each of `from:` (or its `sender:` alias), `to:`, `tag:`, `has:attachment`, `before:YYYY-MM-DD`, and `after:YYYY-MM-DD`. Values with spaces can be quoted, for example `tag:"Client Project"`; text such as `in:inbox` inside a quoted tag value stays part of that value, not a folder choice. `from:` and `to:` are exact address matches. `before:` excludes its date; `after:` includes its date. Choose the folder separately rather than typing a top-level `in:` into the saved query. Boolean `AND`/`OR`/`NOT`, recognized filters with unsupported prefixes such as `-from:alice`, `is:starred`, unknown operators, duplicate filters (including `from:` plus `sender:`), and invalid dates are rejected with an explanation. Repeating sender filters does not create a sender group.

Each view opens `/search` with its query, `scope=mail`, `mode=keyword`, and a stable view ID. The results are fetched from the search Worker page by page, not from the inbox rows already loaded in the browser. Its Next button requires a verified live result beyond the current page; the shareable URL carries a bounded cursor and previous-page trail, so browser Back and Previous retain the correct page even when stale index hits are skipped. Search totals are estimates and do not control this Next button; the sidebar does not show counts. Verification scans at most the first 1,000 indexed hits. If that bound is reached without confirming an end, the page warns that later mail may exist rather than claiming there are no more results. Views are independent and may contain the same message. They do not affect Important/category tabs or move mail. All mail excludes deleted messages. Deleting a view deletes only its definition. A failed or conflicting save leaves the edit in the form for review; the latest account views are available to compare before retrying.

The [saved-view API contract](/components/cookie-worker#saved-mail-views-api) describes the revision check and limits.

## Synced composer preferences

Settings > Email signature and Settings > Compose snippets save to the authenticated Cookie account. A new browser loads them when the user signs in; the signature fills new messages, and saved snippet triggers appear in the composer slash menu. Edits are committed only after the server accepts a save. If another session saved first, Cookie displays the latest account values and keeps the local draft for review.

Snippets can include `{{recipient.first_name}}`, `{{recipient.name}}`, and `{{recipient.email}}`, plus editable fields such as `{{fill:meeting time}}`. Type a saved slash trigger in a new message or inline reply to preview it, review suggested recipient values, and fill the fields before inserting. Cookie uses a recipient name only when it matches one selected address; if the name is unavailable or there are several recipients, enter the value yourself. Values are inserted as text, not HTML. Unfilled fields remain visible in the draft, and Send, Send Later, and inline reply Send warn and stop until those fields are filled or removed. Other brace text and older snippets remain literal and continue to work.

This expansion and send check currently belongs to Cookie-Web. Clients that consume the shared `id`/`name`/`html` snippet records, including a future mobile snippets UI, need equivalent expansion and unresolved-field checks before sending.

Older browser-local signature and snippet values are never assigned to an account automatically. If this browser has them, Settings previews the old values and offers checkboxes to replace the account's signature, snippets, or both. Only values chosen in a successful import are removed from the old browser keys. Signing out clears the active in-memory composer preferences and draft; there is no account-scoped browser cache for these preferences.

The cross-client API contract is documented in [Cookie-Worker's composer preferences section](/components/cookie-worker#composer-preferences-api). Mobile clients can reuse it without adopting Cookie-Web's Settings UI.

## Share availability from a draft

Choose **Share availability** below the editor in a new message or inline reply. Select a date range of at most 31 days, a meeting duration, working hours, a proposal timezone, and up to ten calendars. All days in the selected range are considered. Cookie shows up to 100 non-overlapping suggestions; select up to ten, choose **Review selected times**, edit the proposal text, and insert it into the existing draft. The inserted text includes the IANA timezone, UTC offsets, and duration. It remains editable and explicitly labels the times as proposals. Inserting them does not create an event, reserve a time, send an invitation, or produce a booking link.

The **Calendar interpretation timezone** is separate from the proposal/working-hours timezone. Cookie's stored event times have no original timezone, and date-only or floating subscription events also need an interpretation. Confirm that zone before checking. Subscribed timed events with an explicit supported timezone retain their source instants. Choose calendars whose floating times can share the confirmed interpretation zone.

Every check reads owned Cookie events and fetches the selected subscriptions afresh for the requested range; it never calculates free time from cached subscription rows alone. Calendar checkboxes show the last cached sync time, whether it is over 24 hours old or failed, and whether the selected range was freshly checked. A fresh availability check does not update the cached calendar or its last-sync timestamp. A failed, excessive, ambiguous, or unsupported calendar check blocks suggestions until the range or calendar selection changes or a retry succeeds. [Availability API limits](/components/cookie-worker#availability-read-api) describe the supported feed forms.

All-day, recurring, overnight, and overlapping events block their busy intervals. Suggestions exclude nonexistent and repeated daylight-saving wall times and meetings that would cross an offset change. Availability can change after the check; the review shows its timestamp, and recipients still need confirmation. Event titles and subscription URLs are never inserted. Signing out or changing accounts clears the shared calendar cache, closes availability review, and ignores outstanding responses from the previous account.

## Tasks and unified search

Cookie's Tasks app stores user-authored work separately from the overnight enricher's email-derived `tasks` rows. It supports a static Inbox, Today (including overdue work), nested projects, editable task details, completion, reassignment, due dates, Todoist-style priorities (P1 most urgent through P4 default, shown as coloured flags in the panel and coloured completion circles in the list), and subtasks through the task panel. A task with a due date also appears on Cookie Calendar on that day (an all-day item, or a thirty-minute slot at its due time), under a "Tasks" toggle in the calendar sidebar; clicking it opens the task in the Tasks app. The calendar reads them from the tasks worker's `GET /task-items?view=calendar&from=&to=` window (at most 100 days).

Labels are managed from a Labels section in the Tasks sidebar and from Settings > Tasks > Task Labels: each has a colour and shows how many tasks carry it, click one in the sidebar to list its tasks across projects, drop a task onto it to tag the task, and rename or delete it everywhere at once. Tasks take labels from a chip picker that suggests existing ones; a new name typed as `@name` is registered with the default colour.

Dividers are rules dropped between rows to group them; each can carry a short heading centred on the rule, edited in place.

The header search is available across applications and routes to `/search`. `cookie-web-search` federates Meilisearch results from the `messages`, `documents`, and `tasks` indexes, then hydrates owned rows from Postgres. Scope tabs can restrict results to mail, documents, or tasks. Mailbox Q&A remains mail-only.

## Documents folder browser and uploaded files

The Documents dashboard is a folder browser: it shows one folder at a time, subfolders first, then documents and uploaded files together by name, as cards or rows (the choice is remembered per browser). A breadcrumb leads back up, and the sidebar tree follows the browser: opening a folder, or a document inside one, expands that folder and its parents so the current location is always visible. Starred, tag, and search views keep the flat table because they cut across folders.

### What can be uploaded

- **Any file type.** There is no allow-list; the only limit is **25 MB per file**. Larger files are refused with `413` before any bytes are stored, and a user may start at most 60 uploads per minute (`429` beyond that).
- **Upload** in the toolbar, or drop files anywhere on the pane, adds them to the folder currently shown. Files can also be dropped onto a folder card, or onto a folder in the sidebar, and moved later from the item menu.
- The file's type is detected from its first bytes for JPEG, PNG, GIF, WebP, and PDF. Anything else keeps the type the browser declared, or `application/octet-stream` when it declares none. The stored name is trimmed to 255 characters.

### Where files live

| Piece | Location |
| --- | --- |
| Bytes | Private Cloudflare R2 bucket `cookie-files`, bound to `cookie-web-tasks` as `FILES`, keyed by `<user_id>/<uuid>` so a key never carries a client-supplied name |
| Metadata | `document_files` in Supabase (name, MIME type, size, folder, owner), migration `0076` |
| Access | Only through the authenticated `cookie-web-tasks` Worker `/files` routes; the bucket is never public and every read checks ownership first |

Files are not indexed for search, cannot be tagged, and are never read by Document AI. Deleting a folder moves its files (like its documents) to the root instead of destroying them; deleting a file removes the metadata row first and then the R2 object.

### Opening and downloading

Image files show a thumbnail of their bytes in place of the icon, in both the grid and the list, fetched through the same authenticated route once the card scrolls into view and cached per file for the session. Images and PDFs, the sniffed types only, open in an inline preview at `/documents/file/<id>`, with a download button. Every other type downloads with its original name. The Worker serves both with `X-Content-Type-Options: nosniff`, so a file uploaded with a misleading declared type is never rendered as something it is not.

## Document editing and bounded lists

Plain tables use a lightweight editable grid with row and column controls; **Open spreadsheet** activates formulas and advanced tools. Existing formula tables and workbook snapshots keep the full spreadsheet editor. Offscreen rich editors retain their stored data until activation, and document blocks become interactive only after Editor.js has installed its change observer.

Large mail and document lists render a bounded window, locating visible rows with binary search. Document/task pages are fetched incrementally. Task deep links load the full task before deciding whether it exists; network failures remain retryable. Creating an AI document completes its save without overriding navigation made while creation was pending.

## Local development

```sh
npm install
npm run dev
```

Without `DATABASE_URL`, local API middleware and Playwright routes use fixture data. Routine validation is:

```sh
npm run format:check
npm run lint
npm run test:unit -- --run
npm run build
npm run test:e2e
```

## Configuration highlights

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | Supabase Postgres connection for migrations and local fixture tooling |
| `VITE_AUTH0_DOMAIN` / `VITE_AUTH0_CLIENT_ID` / `VITE_AUTH0_AUDIENCE` | Browser Auth0 configuration |
| `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` | Content-free Realtime inbox pings |

The `/api/send` adapter forwards bearer-authenticated requests to the fixed send Worker origin. Delivery credentials, quotas, reminder validation, tracking pixels, and sent-copy persistence are owned by Cookie-Worker. A failed client send preserves its request ID for retry; a confirmed send releases it so identical new mail can be sent intentionally.

The Worker API origins are public constants in `src/lib/apiWorkers.js`, not environment secrets.

Pushes to `main` run format, lint, unit, build, and Chromium end-to-end jobs. Vercel deploys the SPA automatically; migration changes also trigger the `Migrate Database` workflow.
