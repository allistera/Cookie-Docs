Each repository owns its validation and deployment surface. Cookie-Web and Cookie-Worker must coordinate schema-dependent releases; Cookie-Agents, Cookie-iOS, and Cookie-Docs validate independently.

## CI and deployment by repository

| Repository | Automated checks | Deployment |
| --- | --- | --- |
| Cookie-Web | Format, Oxlint/ESLint, unit tests, production build, Chromium and Firefox Playwright | Vercel deploys pushes to `main`; migration changes also run `migrate.yml` |
| Cookie-Worker | Format, lint, generated-type check, repository typecheck, unit tests, `dry-run --all` | Manual `Deploy` workflow; default `all` publishes all thirteen sequentially, or one Worker can be selected |
| Cookie-iOS | SwiftLint, XcodeGen project generation and the unit-test bundle on an iPhone Simulator | Main runs archive/sign and upload to TestFlight after lint and native tests pass |
| Cookie-Agents | Ruff, Pytest, and Docker image build | Render Blueprint auto-deploys the API on `main`; separate workflow publishes static API docs |
| Cookie-Docs | Format and production build | GitHub Pages workflow deploys `dist/` from `main` |

Cookie-Worker deploy validation always checks the whole repository before publishing. A single-Worker selection then dry-runs that capsule once more; `all` publishes the discovered Workers in workflow order under one production concurrency lock.

## Deploying Worker and schema changes

1. Apply any Cookie-Web migration first. Runtime code must tolerate the old schema until the migration is present.
2. Run the Cookie-Worker validation suite and a selected-worker dry-run.
3. Dispatch `Deploy` with `all` or the exact directory name under `workers/`.
4. Verify the changed path in production. For inbound mail, confirm forwarding, durable storage, classification, and indexing; for browser APIs, confirm Auth0, CORS, and the custom domain; for service bindings, verify both caller and target logs.
5. Inspect Sentry by `service` and `operation` tags, and the Worker's Honeycomb dataset for latency. [Observability](/observability) lists every signal and where it lands.

Cookie-Worker's `RUNBOOK.md` contains the detailed production, search-repair, rotation, incident, and rollback checklists.

### Calendar invitations

Roll out in this order: merge Cookie-Web (migration `0113` runs from `main`), deploy `cookie-web-messages` and `cookie-web-send`, then let Vercel publish the web client. Before the migration the messages Worker logs `calendar_invitation_sync_failed` and returns no invitation, so the reader keeps its **Add to calendar** offer; nothing fails.

The automated tests run the whole flow on PostgreSQL with a stand-in for the mail provider. Whether an organiser's calendar accepts the reply can only be seen with real mailboxes, so check it once after the first deploy, and again after any change to the reply's content:

1. From a second mailbox with a calendar (a Google account and an Outlook.com account cover the two common organisers), invite the address Cookie sends as (`EMAIL_FROM`) to an event.
2. Open the invitation in Cookie. Confirm the organiser has received nothing, then press **Accept**. The organiser's event should show the guest as accepted, and the organiser's inbox a mail titled "Accepted: …" with `invite.ics`.
3. Press **Decline** and confirm the organiser's event follows.
4. Change the event's time from the organiser's calendar. Open the update in Cookie: the card shows the new time with no answer, and Cookie's calendar has one entry at the new time.
5. Delete the event from the organiser's calendar. Open the cancellation in Cookie: the card reads cancelled and the entry is gone.
6. Invite a different address of the same person (the Gmail address their mail is forwarded from). The card should explain that Cookie cannot answer for it, and the organiser should receive nothing.

If the organiser gets the mail but their calendar does not move, compare the received `invite.ics` part's `Content-Type` with `text/calendar; charset=utf-8; method=REPLY`: a provider that drops `method` turns the reply into a plain attachment.

### Cc and Bcc

Roll out in this order: deploy `cookie-web-send` and `cookie-web-drafts` from Cookie-Worker, then merge Cookie-Web (migration `0114` runs from `main` and Vercel publishes the client that offers the two lines). The Workers come first here because a Worker that predates the change ignores `cc` and `bcc`: a message sent through it would go out without the people copied on it, and nothing would say so.

Those Workers run with or without the migration. In the short time between Vercel publishing the client and the migration finishing, a draft or a Send Later that has a Cc or Bcc line fails to save and says so; an immediate send is unaffected.

To check it after the rollout, send a message from the composer with one address on Cc and another on Bcc. Each should receive it, the Cc recipient should see the Cc line and no Bcc, and the Sent copy's `recipients` should hold all three lines.

### September review fixes

Deploy `cookie-web-send` with follow-up support **before** the Cookie-Web compatibility adapter. Apply Cookie-Web migration `0065_task_subtree_projects.sql` to repair children left in old projects and index parent lookups. The updated tasks Worker moves each complete subtree in a transaction and serializes structural changes per owner. Deploy it promptly with the repair so older handlers cannot recreate the inconsistency.

Run the search drift repair after deploying the indexing changes; older incorrectly stamped rows may require a one-time full reindex. Calendar schema fallbacks remain supported until every deployment is verified beyond migrations 0024–0027. Removing those branches is conditional on that inventory, not on the presence of migration files in the repository.

## Search operations

- `Search Reindex` rebuilds the Meilisearch indexes from owned Postgres rows and configures the OpenAI embedder used by Meilisearch.
- `Search Drift Repair` repairs rows whose `search_indexed_at` watermark trails the row or a task's subtasks.
- Runtime Workers do not call `/v1/embeddings`; they write documents to Meilisearch, which owns embedding generation.

The API keys used for runtime Responses calls and the reindex embedder may therefore require different scopes even when they share the `OPENAI_API_KEY` repository-secret name.

## Secrets and bindings

Worker secrets are synchronized only to the capsules that need them. Common examples are `SENTRY_DSN`, `OPENAI_API_KEY`, `MEILISEARCH_API_KEY`, and `BLOB_READ_WRITE_TOKEN`; `EMAIL_FROM` and `RESEND_API_KEY` for `cookie-web-send` are retained as Cloudflare secrets once set.

Two cross-Worker pairs must agree:

- `cookie-web-tasks` → `data-enricher`: service binding plus matching trigger token.
- `scheduled-send-flusher` → `cookie-web-send`: `SEND` service binding plus matching flush bearer secret.

`cookie-web-tasks` also binds the private R2 bucket `cookie-files` as `FILES` for files uploaded to Documents. Create it once with `wrangler r2 bucket create cookie-files`; the bucket is never made public, and bytes are served only through the Worker's `/files/:id/content` route.

Vercel holds Cookie-Web's browser build and migration settings; the compatibility send adapter forwards delivery to the Worker. Composer attachment uploads go from the browser to `cookie-web-send` directly, so Vercel needs no Blob storage or database settings for them. Render holds Cookie-Agents' API key, Gmail OAuth credentials, optional Todoist token, and managed-database configuration. GitHub Pages needs no runtime Cookie data secrets.

## Local-development safety

Never point routine Cookie-Web or Cookie-Worker development at the production Supabase database. Cookie-Web can use fixtures without `DATABASE_URL`; Worker development requires a separate Supabase project. Cookie-Agents is isolated and may use its Docker Compose PostgreSQL volume because it does not share the mail-app schema.

## Review remediation rollout

The October 2026 remediation introduces three additive migrations owned by
Cookie-Web: 0102 binds Google authorization completion to its original browser
and account; 0103 records object deletion jobs and document-image references;
0104 journals outbound delivery attempts and sent-copy reconciliation.
Apply these through the normal reviewed migration process before deploying the
corresponding Workers, then deploy the Web client. Existing unbound Google
authorization attempts must be restarted. Legacy ambiguous scheduled sends
require review rather than an automatic fresh retry window.

The Processing mailbox keeps mail available when AI classification is deferred
or unavailable. It does not bypass sender screening, and its warning makes clear
that spam classification is incomplete. Draft recovery and failed offline edits
are visible in the client; local copies are scoped to the signed-in account.

Monitor durable delivery reconciliation, object cleanup retries and search-drift
age after rollout. An accepted delivery with a missing sent copy is repaired
without contacting the provider to send again. An uncertain delivery needs
operator review before any replacement send. Preserve the new ledger and queue
tables during application rollback.

Dependency audits run in pull-request CI. Cookie-Docs has one temporary
unpatched transitive CLI advisory documented in `SECURITY.md`; its exception
expires on 20 November 2026. The documentation check workflow builds pull
requests without deploying GitHub Pages.
