Each repository owns its validation and deployment surface. Cookie-Web and Cookie-Worker must coordinate schema-dependent releases; Cookie-Agents, Cookie-iOS, and Cookie-Docs validate independently.

## CI and deployment by repository

| Repository | Automated checks | Deployment |
| --- | --- | --- |
| Cookie-Web | Format, Oxlint/ESLint, unit tests, production build, Chromium Playwright | Vercel deploys pushes to `main`; migration changes also run `migrate.yml` |
| Cookie-Worker | Format, lint, generated-type check, repository typecheck, unit tests, `dry-run --all` | Manual `Deploy` workflow; default `all` publishes all thirteen sequentially, or one Worker can be selected |
| Cookie-iOS | XcodeGen project generation and the unit-test bundle on an iPhone Simulator | No automated distribution; archive/signing remain local Xcode responsibilities |
| Cookie-Agents | Ruff, Pytest, and Docker image build | Render Blueprint auto-deploys the API on `main`; separate workflow publishes static API docs |
| Cookie-Docs | Format and production build | GitHub Pages workflow deploys `dist/` from `main` |

Cookie-Worker deploy validation always checks the whole repository before publishing. A single-Worker selection then dry-runs that capsule once more; `all` publishes the discovered Workers in workflow order under one production concurrency lock.

## Deploying Worker and schema changes

1. Apply any Cookie-Web migration first. Runtime code must tolerate the old schema until the migration is present.
2. Run the Cookie-Worker validation suite and a selected-worker dry-run.
3. Dispatch `Deploy` with `all` or the exact directory name under `workers/`.
4. Verify the changed path in production. For inbound mail, confirm forwarding, durable storage, classification, and indexing; for browser APIs, confirm Auth0, CORS, and the custom domain; for service bindings, verify both caller and target logs.
5. Inspect Sentry by `service` and `operation` tags.

Cookie-Worker's `RUNBOOK.md` contains the detailed production, search-repair, rotation, incident, and rollback checklists.

## Search operations

- `Search Reindex` rebuilds the Meilisearch indexes from owned Postgres rows and configures the OpenAI embedder used by Meilisearch.
- `Search Drift Repair` repairs rows whose `search_indexed_at` watermark trails the row or a task's subtasks.
- Runtime Workers do not call `/v1/embeddings`; they write documents to Meilisearch, which owns embedding generation.

The API keys used for runtime Responses calls and the reindex embedder may therefore require different scopes even when they share the `OPENAI_API_KEY` repository-secret name.

## Secrets and bindings

Worker secrets are synchronized only to the capsules that need them. Common examples are `SENTRY_DSN`, `OPENAI_API_KEY`, `MEILISEARCH_API_KEY`, and `BLOB_READ_WRITE_TOKEN`; `EMAIL_FROM` and `RESEND_API_KEY` for `cookie-web-send` are retained as Cloudflare secrets once set.

Two cross-Worker pairs must agree:

- `cookie-web-tasks` → `data-enricher`: service binding plus matching trigger token.
- `scheduled-send-flusher` → `cookie-web-send`: `SEND` service binding plus matching flush bearer secret.

Vercel separately holds Cookie-Web's compatibility-send and migration settings. Render holds Cookie-Agents' API key, Gmail OAuth credentials, optional Todoist token, and managed-database configuration. GitHub Pages needs no runtime Cookie data secrets.

## Local-development safety

Never point routine Cookie-Web or Cookie-Worker development at the production Supabase database. Cookie-Web can use fixtures without `DATABASE_URL`; Worker development requires a separate Supabase project. Cookie-Agents is isolated and may use its Docker Compose PostgreSQL volume because it does not share the mail-app schema.
